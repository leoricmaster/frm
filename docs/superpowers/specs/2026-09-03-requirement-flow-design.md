# 产研需求流设计（受理—追溯—可视化）

- 日期：2026-09-03
- 状态：已与发起人逐节确认
- 依据：[统一代码管理体系设计](./2026-08-31-excavator-code-management-design.md) §4.1/§6.3/§6.4/§7.2/§7.3、[Harbor / MinIO 二阶段验证设计](./2026-09-01-harbor-minio-phase2-design.md)
- 定位：补齐总设计中缺位的"需求侧"——总设计已覆盖代码→MR→CI→制品→发布的链路（§6），但需求/缺陷以什么形态进入这条链、管理者如何看到进度，尚无机制。本设计用 GitLab CE 原生能力补上这一环，并以 gitlab-compose-test 三阶段原型验证。

## 1. 背景与问题

- 需求与缺陷的提出、跟踪目前靠口头与 Excel，无任何工具承载；
- 来源分散：集团/市场/客户/现场反馈/跨组协作，无统一入口，需求散落在群消息与个人备忘里；
- 交付为版本制、节点驱动（非固定迭代），管理层看不清"需求到哪了、卡在哪"；
- 团队在需求管理与流程化方面经验有限，方案必须**实用、简洁、高效**，流程摩擦足够小，否则口头文化会把任何规范击穿。

## 2. 已确认的关键决策

| 决策点 | 结论 |
|---|---|
| 范围 | 需求→发布全链路可追溯 + 跨团队进度可视化；不含四类仓库接入 CI 的构建细节（属阶段 2/3 既有内容） |
| 现状 | 无既有工具，绿地引入 GitLab Issues，无迁移/对接负担 |
| 节奏 | 版本制、里程碑组织，不搞固定迭代、不搞工时统计 |
| 方案 | GitLab 原生轻量需求流（见 §3 选型） |
| 产出 | 设计文档 + gitlab-compose-test 三阶段原型验证 + 教程，与前两阶段同套路 |

## 3. 方案选型

- **方案 A：GitLab 原生轻量需求流（选定）**——需求单（Issue）与代码同库同系统，追溯链由系统自动生成（MR 关单、tag 挂里程碑），零新增运维，CE 免费能力足够。
- 方案 B：专业需求工具（禅道/飞书项目）+ GitLab 打通——需求管理能力强，但双系统双录入、同步需开发维护、审计链跨系统断裂；经验有限的团队先背工具再背流程。作为集团将来强制统一工具时的对接预留（本设计的制度与工具无关，数据可导出迁移）。
- 方案 C：规范化 Excel + 例会——不解决追溯与可视化，口头文化击穿任何表格规范，否决。

选定 A 的根本理由：流程成败不在工具功能多寡，而在**流程摩擦是否足够小**——A 方案里"提单→合码→发布→追溯"每一步都被系统自动串联，人只需要养成一个新习惯（提单），其余顺路完成。

## 4. 流程骨架

### 4.1 统一受理台

顶层 group 下新增仓库 **`excavator/intake`（受理台）**，所有来源只有一个进料口：

- **谁能提**：全员 Guest 起步（Guest 有建 issue 权限、无代码权限，正好匹配市场/客服提需求的场景）；集团/客户等无账号者由市场或 PM **代提**，单上标注真实来源；
- **怎么提**：三个 issue 模板三选一——`需求`（背景/目标/验收标准）、`缺陷`（现象/复现/影响范围/**机器 manifest 粘贴区**）、`任务`（技术改进类）；
- **来源打标**：建单时选 `来源::集团 / 市场 / 客户 / 现场 / 内部` scoped 标签，将来统计需求来源构成有数据可依。

受理台独立成仓库的代价是多一步移交，换来提单人不需要知道代码住哪——多来源场景下这是必要隔离。

### 4.2 分诊值班

- 每个产品域指定 1 名分诊人（仓库 Owner 兼任，周度轮值亦可）；
- 动作三个：**移交**（move 到对应域仓库，评论与链接全保留）／**打回**（信息不足退回补充）／**婉拒**（重复或超范围，说明理由关闭）；
- **SLA：3 个工作日内完成分诊**。入口响应速度决定大家愿不愿意提单，这是口头文化能否被替代的胜负手。

### 4.3 工作项状态机（全组统一 scoped 标签，形如 `状态::待受理`）

```
待受理 ─分诊─→ 已排期 ─→ 开发中 ─→ 已关闭        （默认路径：MR 写 Closes，合入即自动关单）
                 │          └─→ 待验证 ─→ 已关闭   （需外部验收的单：合入后进，验收人手关）
                 └─→ 暂缓 ─恢复─→ 已排期
分诊打回：待受理 单退回提单人补充；已关闭 验收不通过 → 重开回 开发中
受理台终态：已拒绝
```

**关单双路径**（一句话讲清）：默认 MR 写 `Closes #单号`，合入即关单——单的完成定义在 MR 内（CI 绿 + 自测 + 评审）；需要**外部验收**（HIL 台架、现场确认、提出方验收）的单，MR 只引用不写 Closes，合入后拖入 `待验证`，验收人通过后手动关单。

7 个状态，一个不多一个不少。看板列即状态，状态即例会议程。

### 4.4 版本节奏（组级里程碑）

- **里程碑 = 版本节点**，命名如 `固件 v2.3·2026Q4批次`，组级里程碑跨仓库生效；
- 排期 = 域 Owner 的月度排期会把单拖进里程碑，进里程碑即打 `已排期`；
- 进度看里程碑完成度（CE 按单数给百分比），不做工时与燃尽。

## 5. 追溯闭环

### 5.1 正向追溯链——从需求到挖机上跑的代码

```
需求单 → MR(描述写 Closes #单号 + 选里程碑) → CI 绿 → 合入自动关单
       → tag + Release(挂里程碑) → manifest.json(内嵌 commit) → 烧进机器
```

**这条链由系统自动生成，不靠人事后补录**：MR 合入时 GitLab 自动在单上记录合入 commit 与关联；Release/里程碑关联让"这个版本收了哪些需求"可一键列出；manifest.json（总设计 §6.3）内嵌 commit hash，制品天然指向整条链。

关单规则见 §4.3 双路径：默认 `Closes #单号` 合入即关；需外部验收的单只引用不写 Closes，走 `待验证` 由验收人手关。

制度兜底只需 MR 模板 checklist：☑ 关联需求单号（Closes 或引用） ☑ 选定里程碑 ☑ CI 全绿 ☑ 自测通过。Maintainer 合码照单核对。

### 5.2 反向追溯链——从现场机器回到需求源头

现场机器出问题 → 维护人员读出 `manifest.json` → 粘贴进缺陷模板 manifest 区 → commit 定位 → 该 commit 经哪次 MR 合入 → 关联哪张需求单——"这个行为是哪次需求引入的"一查便知。

与驻场教程已有的 manifest 核对流程无缝衔接；现场"改代码必须走 MR 回中心"的铁律（总设计 §7.3）自动落进需求体系，**现场改动天然有单**。反向链依赖"现场只刷 CI 签名制品"铁律的执行力——临时包刷入的机器 manifest 链是断的，由应急 24h 补单机制记账。

### 5.3 跨域大需求拆解（CE 无 epic 的轻量替代）

总单留在牵头的域仓库（牵头域未明确时暂留受理台），描述里用任务清单逐条"转换为 issue"生成各域子单，子单用 related issues 回链总单。只有子单进开发状态，总单是视图不是工作项。长需求文档先以 issue 描述为权威，确有需要再升级为仓库内 Markdown 文档（YAGNI）。

## 6. 进度可视化（全部 CE 免费）

| 视图 | 怎么用 |
|---|---|
| **组级看板**（列=状态） | 按里程碑过滤（如"固件 v2.3"），一屏看全域当前状态 |
| **里程碑完成度** | 按单数百分比 + 已关/未关清单，管理者例会投屏 |
| **受理台积压** | intake 仓库按 `待受理` 过滤，分诊堵没堵一眼可见 |

配套纪律：**周例会只看板、不念稿**——"待验证挂了一周的单"自动成为议程。

## 7. 制度与配置归属

### 7.1 三无制度（宪法级，与既有铁律同级）

写入 `platform/` 宪法仓库，规则变更走 MR：

1. **无单不开发**——任何改动（需求、缺陷、现场修复）先有单，commit 必须能追到一张 issue；
2. **无 MR 不合码**——既有规则（禁直推 main）复述入宪法；
3. **无里程碑不发布**——tag/Release 必须挂里程碑。

### 7.2 角色与配置归属（零新增角色）

| 现有角色 | 增量职责 |
|---|---|
| 提单人（市场/客服/集团，Guest） | 按模板建单，仅此而已 |
| 分诊人（域 Owner 兼任） | 3 日内移交/打回/婉拒 |
| 域 Owner / Maintainer | 排期（拖里程碑）、合码核 checklist |
| 管理者（Reporter） | 周例会看板投屏 |
| 平台工程师 | **标签字典、看板配置、模板**全部在 platform/ 仓库版本化——新增标签也走 MR，防止标签蔓延失控 |

### 7.3 防滥用边界

- 单据质量：验收标准必填 + 分诊打回兜底；
- 口头文化残留：例会只看板；群里的需求一概回"请提单"；
- 敏感信息：模板注明不贴客户商务/合同细节（DLP 意识延伸到需求侧）。

## 8. 原型验证设计（gitlab-compose-test 三阶段）

| 场景 | 验证内容 |
|---|---|
| 1 多来源建单与分诊 | Guest 建单、代提、移交域仓库、打回、婉拒各留证据 |
| 2 正向全链 | 域仓库单 → MR(Closes) → CI 绿 → 合入自动关单 → tag/Release 挂里程碑 |
| 3 现场反向追溯 | 读 manifest → 建缺陷单 → 定位 commit → 回到需求单 |
| 4 管理视图 | 组看板状态列、里程碑过滤与完成度、受理台积压视图 |

交付物：

- 原型实例配置落位：intake 仓库、issue/MR 模板、scoped 标签字典、组看板、组里程碑；
- 截图证据链（编号续 32 起，存 `gitlab-compose-test/screenshots/`）；
- test-plan 新增"第三阶段验证结果"章节；
- 教程：新增第 6 篇《需求提出人与管理者》（提单 + 看板视角）；小幅扩展 developer（提单/关联单号）与 field-engineer（manifest 建缺陷单）教程——教程不先于验证，按实际路径补。

## 9. 落地节奏（参考，不写死）

1. 原型验证 + 制度文档定稿；
2. 正式实例配置（标签/看板/模板/受理仓库）+ 各域指定分诊人；
3. 与存量代码收编（总设计阶段 2）并行推进——收编本身就用任务单驱动，正好练手。

## 10. 风险与应对

| 风险 | 应对 |
|---|---|
| 提单人嫌麻烦，绕回口头（最大风险） | 模板足够短、Guest 权限门槛足够低；分诊 3 日 SLA 给正反馈；例会只认板上的单，群消息一概"请提单" |
| 分诊人成为新瓶颈 | 受理台积压视图暴露问题；域 Owner 轮值分诊；积压超一周在例会上点名 |
| 标签与状态蔓延 | 标签字典进 platform/ 宪法仓库，新增走 MR |
| 单据质量差、验收标准空泛 | 分诊打回机制；模板示例文案给"好单"的样子 |
| CE 能力边界（无 epic/燃尽/工时） | 设计已用任务清单拆单、按单数百分比、里程碑清单平替；真成为痛点再评估升级 Premium 或对接专业工具（方案 B 预留） |
| 集团将来强制统一需求工具 | 制度与工具无关，规则可整体搬迁；issue 数据可导出 |

## 11. 明确不做

固定迭代、工时统计、燃尽图、epics、DORA 度量、外部需求工具对接、发布说明自动生成（先手工复制里程碑清单，量大了再自动化）。
