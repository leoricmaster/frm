平台工程上手指南

管 platform/ci-templates——全项目 CI 规则的唯一来源，变更权只在本组

platform 组 Maintainer

你是谁

你是这个项目的平台工程，在 GitLab 里的角色是 platform 组 Maintainer：管 platform/ci-templates——全项目 CI 规则的唯一来源，变更权只在本组（实测见测试计划 §7.3-5：firmware 维护者推本仓库被 403 拒绝）。连业务仓库的 Owner 都动不了模板——这不是不信任谁，而是把"规则怎么变"收拢成一条唯一的通道：MR + 评审。

你能做什么 / 不能做什么

能 ✅不能 ❌
改 ci-templates 并走 MR 合入直接改业务仓库的代码
管 runner 注册与标签跳过 MR 直推 ci-templates 的 main
管 Harbor 项目与 MinIO 桶策略把 Harbor/MinIO 凭据写进仓库或教程
制定下游流水线准入规则在业务仓库里单独给某个仓库开后门

典型任务流：一次模板变更的合入与传播验证

1

认识模板仓库

打开 platform/ci-templates，里面是四套业务模板和配套规范文档——全项目的流水线长什么样，由这里说了算。

🔍 为什么叫"宪法"？ 规则版本化、变更走 MR 评审，避免口头规矩（§4.1）——规则躺在仓库里、有 commit 历史可查，比"群里说一声大家改一下"可靠得多。
2

改模板

和业务开发同款节奏：分支 → 修改 → push → MR。main 受保护，直推会被拒，一切变更走 MR。

$ git checkout -b fix/artifact-empty-check
$ git push -u origin fix/artifact-empty-check
3

合入即全下游生效

下游各仓库的 .gitlab-ci.yml 里是 include + extends，模板改动无需任何下游仓库配合（§6.2）——你合入 MR 的那一刻，新规则就已经挂在所有人的流水线定义上了。

4

验证传播

随便挑一个下游仓库触发新流水线 → 打开 build job 看 Trace：出现模板新增的"产物为空，禁止发布"校验，即证明传播成功。

5

把规则写进准入

下游流水线不 include 通用层的 MR 不予合入（§6.2 制度 + 自检双保险）——制度上卡 MR 准入，自检上让流水线自己报错，两层兜底。

🔍 机制：include 在流水线创建时解析并快照 retry 不重新解析；模板热修后必须触发新流水线验证，别盯着旧流水线 retry（§7.3-4 实测）——旧流水线用的还是创建那一刻的模板快照，retry 一百次也看不到新规则。

典型任务流：纳管镜像仓库与对象存储

二阶段（2026-09-01）把 Harbor（镜像仓库）和 MinIO（对象存储）接进了原型——这两件的基础设施也在你手上：建项目、配桶策略、把凭据安全地交给 CI。下面是配置到位后的全貌（设计 §6.4 产物归宿、§5.3 出口收敛、§6.5 密钥管理；验证证据见测试计划 §8）。

1

Harbor 两项目

Harbor 里建两个项目，分工不同：

  • frm-ci——业务镜像直推区：CI 构建完镜像 push 进这里，再 pull 回 runner 验证（build→push→pull 回验，设计 §5.3）。
  • docker-hub-proxy——代理缓存区：上游配 docker.1ms.run，构建区拉 base 镜像走这里而不直连外网。
🔍 为什么构建区拉包必须走代理？ 构建区无外网直连，pip/npm/docker 拉包一律走内网 Harbor 代理——出口收敛、日志可查，哪个 job 拉了什么镜像有迹可循（设计 §5.3）。
2

MinIO 三桶

MinIO 起三个桶，对应三类大文件（设计 §6.4）：

  • dataset-model——数据集与模型权重实体，git 里只存清单 datasets.manifest.json 与 sha256 指针。
  • field-dropzone——现场数据投放区，write-only 策略：现场只能往里投，不能删、不能列别人的。
  • training-output——训练产物入库，配 manifest.json 写 s3 指针，CI 凭它取回。
🔍 为什么大文件不进 git？ 数据集、模型权重动辄 GB 级，进 git 仓库会撑爆、clone 变慢、历史污染——git 只存清单与指针，实体放对象存储（设计 §6.4）。
3

CI 凭据受保护 + 打码

Harbor robot account 与 MinIO access key 不进仓库，配成 GitLab 受保护变量（protected + masked）：只在受保护分支/标签的流水线里可见，job 日志里凭据一律显示 [MASKED]。

🔍 为什么凭据要打码？ CI 日志谁都能翻——凭据打码让日志可共享排查（红了一起看日志）却不会泄露密钥；明文凭据走受控主机、不进流水线（设计 §6.5）。

典型任务流：纳管需求流配置（三阶段新增）

三阶段引入了需求流——受理台、scoped 标签字典、组看板、issue 模板——这些配置的版本化管护也在你手上（§7.2）。所有需求流配置都在 platform/ 仓库里走 MR，与 ci-templates 同级管理：新增一个标签也走 MR，防止标签蔓延失控。

1

scoped 标签字典

全组统一的两套 scoped 标签在 platform/ 仓库版本化（§4.3）：

  • 状态::——7 个：待受理 / 已排期 / 开发中 / 待验证 / 已关闭 / 已拒绝 / 暂缓。一个不多一个不少——看板列就是这 7 个状态。
  • 来源::——5 个：集团 / 市场 / 客户 / 现场 / 内部。统计需求来源构成有数据可依。

新增或改名一个标签 = 改 platform/ 里的标签字典文件 → MR 评审 → 合入。不走 MR 直接在 GitLab 界面加标签 = 绕过版本化，不允许。

🔍 为什么标签也走 MR？ 标签是看板列、是统计维度、是例会议程——一个人随手加一个标签，看板就多一列、统计就对不齐。版本化让标签变更可追溯、可评审（§7.2）。
2

组看板与里程碑配置

组级看板的列配置（7 状态列）和组级里程碑（版本节点）都在 platform/ 里管。看板是懒创建的——首次浏览器访问后 API 才能加列，这个坑三阶段实测踩过（test-plan 9.1）。里程碑命名规范如 固件 v0.9·三阶段原型，跨仓库生效。

🔍 为什么看板列 = 状态标签？ 看板列不是自由配置的——它直接映射 7 个 scoped 状态标签。改列 = 改标签字典 = 走 MR（§4.3 / §6）。
3

issue 模板与 MR 模板

受理台的三个 issue 模板（需求 / 缺陷 / 任务）和各域仓库的 MR 模板（含需求流四项 checklist）都在 platform/ 版本化。改模板 = 改所有人的提单/建 MR 体验，必须走 MR 评审——与改 ci-templates 同理。

🔍 为什么模板也在 platform/？ 模板是流程的入口——模板改一行，所有人的提单/建 MR 行为就变了。与 ci-templates 同理，集中版本化、走 MR 评审、防止各域各搞一套（§7.2）。

常见报错自救

💡 下游报 ci-templates not found or access denied 检查该开发者是否在 platform 组有 Reporter（全员可读是硬规则，§7.3-1）——通用层人人可读、只有本组可写，漏加读权限是这类报错的头号原因。
💡 下游 job 用了自写 script，不吃模板更新 它只 include 没 extends——改它的 job 定义，加上 extends: .firmware-template，让模板规则真正接管这个 job（§7.3-2）。

红线清单

🚫 标签/看板/模板不在 GitLab 界面直接改——走 platform/ MR 直接在 GitLab 界面加标签、改看板列、改模板 = 绕过版本化，不可追溯、不可评审（需求流设计 §7.2）。
🚫 模板改动必须自己先在测试仓库跑绿再合入 你影响的是所有仓库——一次没验证的合入等于同时给四套业务线埋雷。
🚫 不给任何业务仓库绕过通用层的后门 一个仓库例外，宪法就名存实亡——特殊需求改模板，不给单独开口子。
🚫 runner 密钥/注册 token 不进仓库、不进聊天工具 泄露即全园区 runner 失守，只走安全渠道下发与轮换。
🚫 Harbor/MinIO 凭据同样不进仓库、不进聊天工具 robot account 与 access key 走受保护变量下发、定期轮换（§6.5）——与 runner 密钥同等级别管理。
