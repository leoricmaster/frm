驻场工程师上手指南

出差在现场的人——离线为基线、有网为加速，流程不赌现场有网

出场前 Developer / 现场 Guest

你是谁

你是这个项目的驻场工程师：在公司里是 Developer，到了现场账号降为 Guest——能下载制品、提问题，但不能改中心仓（§7 开篇）。你的一切工作围绕一条设计原则展开：离线为基线、有网为加速——流程不赌现场有网。出场前把该拿的都拿全，现场三类工作各走各的通道，极端情况有应急兜底、但兜底也有账可查。

你能做什么 / 不能做什么

能 ✅不能 ❌
出场前 clone 代码、下载已签名制品现场编译正式版本
现场本地 commit 改码验证改动不留 commit（=违规）
应急刷本地临时包（须 24h 内补 MR）把临时包当工作方式

典型任务流：一次驻场任务的全程

1

出场前打包（公司内）

在公司把"弹药"备齐：git pull 同步代码，再从 Release 下载本次任务相关的已签名制品，按目标机器版本打包。

$ git pull
$ # 从 GitLab Release 页下载 .bin 与 manifest.json

按 platform/ 仓库里的出场 checklist 核对：代码、制品、工具链版本、联系人——四样缺一，现场就可能卡死（§7.1）。

2

现场通道一：调试 / 刷固件

只刷预构建制品，刷之前核对 manifest 四字段：name / commit / build_time / runner——确认手上这个包是哪个版本、什么时候、在哪个 runner 构建的（§6.3）。

🔍 为什么现场永远不编译？ 现场产物不可追溯，且编译环境不可控（§7.2）——机器上跑的每一版都必须能回答"源码是什么、谁构建、谁签名"，本机凑合编一个就把这条追溯链打断了。
3

现场通道二：改码

bug 修复、参数调整都在 DLP 笔记本上本地 git commit（哪怕没网）→ 有网即 push → MR → CI 出包 → 下载刷入（§7.2）。

DLP 笔记本（装了集团透明加解密软件的电脑，硬盘上的代码自动加密）——代码拷出去打不开，所以改动回中心仓既是制度要求，也是你唯一安全的备份方式。

改动必须以 commit 回中心仓——这是防止代码重新散落回个人电脑的硬规则：体系好不容易把代码收进 GitLab，一次"改完不交"就又退回 U 盘时代。

4

现场通道三：取数

日志、传感器数据进 MinIO 投放区（field-dropzone 桶）——现场能连则直传，否则回公司上传（§7.2）。

🔍 为什么投放区是 write-only？ 现场只能往里投数据，不能删、不能列别人投的——防数据互覆盖与越权取阅（§7.2）。回公司后由平台组把投放区数据归档进 dataset-model 桶的 field-archive/ 目录留档。

方向单一：数据向内流、代码向外只走 git——两条单向道，审计才简单。

5

应急兜底

断网 + 机器急等，等不了回公司出包？允许本地临时包先刷，但回公司 24 小时内补齐 MR 和正式构建（§7.3）。

🔍 临时包是救火用的，不是工作方式 （§7.3 原话）——24h 补单制度就是"留应急缝，但缝有账可查"：缝给极端情况留着，账让每次应急都回到追溯链上。

常见报错自救

💡 现场没网，改完码怎么办？ 改动已在本地 commit 就安全（不会丢）——回网后 git push -u origin <分支>，再建 MR，改动就能回中心仓。
💡 机器上版本不明，刷什么？ 找到 manifest.json，看 name / commit / build_time / runner 四字段——直接对出这是哪个 commit、何时构建的哪个版本，再决定往上刷哪一版。
💡 现场没网，采集的数据怎么办？ 数据先存本地，回公司连上网再传进投放区——和改码一样"离线为基线、有网为加速"，不赌现场有网。

红线清单

🚫 改动不以 commit 回中心仓 = 按违规处理 （§7.3）——代码只活在你的笔记本上，等于体系对你失效。
🚫 应急临时包超 24h 不补 MR = 违规 应急缝只留给急情，不补单就是把例外变成常态。
🚫 现场数据只进 MinIO 投放区，不走私人网盘 / U 盘乱拷 按 §7.4 集团外发策略走审批加密盘——数据向内流是对体系的方向要求，也是对集团的安全要求。
