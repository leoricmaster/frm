仓库 Owner 上手指南

这个仓库的守门人和发布责任人（每仓库仅 1–2 人，§4.3）

Maintainer 40

你是谁

你是这个仓库的 Owner，在 GitLab 里的角色是 Maintainer（40）：这个仓库的守门人和发布责任人（每仓库仅 1–2 人，§4.3）。Developer 把 MR 修到全绿后，等你评审、等你合入；什么时候打 tag、要不要放行晋升，由你拍板。代码进 main 的最后一道门、制品流向现场的第一个关口，都在你手上。

你能做什么 / 不能做什么

能 ✅不能 ❌
approve 并合入 MR改 platform 组的 ci-templates（平台组自己管）
配保护分支、管成员跳过评审合入自己的 MR（制度）
打 tag、批准晋升、建 Release在本机编发布产物

典型任务流：分诊与排期（需求流）

三阶段起，你不只是代码守门人——你还是这个域的分诊人（§4.2）。提单人在受理台（excavator/intake）提的单，先到你手里过一道：3 个工作日内决定它的去向。

1

分诊：三选一

打开受理台（excavator/intake）的 Issues 列表，按 待受理 过滤——这些单等着你处理。对每张单做三件事之一：

  • 移交——单属于你管的域？把它 move 到你的域仓库，评论与链接全保留。同时代打 来源:: 和 状态::已排期 标签（提单人是 Guest，没有打标权限，标签由你代打，§4.1）。
  • 打回——验收标准空泛、信息不够？退回提单人补充，在评论里写明缺什么。
  • 婉拒——重复提了、或超出本域范围？说明理由、关闭。
🔍 为什么 3 日内必须分诊？ 入口响应速度决定大家愿不愿意提单——这是口头文化能否被替代的胜负手（§4.2）。堵没堵，看受理台积压（见管理者教程的积压视图）。
2

排期：拖里程碑

移交到域仓库的单默认进 已排期。排期 = 把单拖进版本里程碑（如"固件 v0.9"），进里程碑即排上日程。里程碑 = 版本节点，跨仓库生效（§4.4）。

🔍 为什么不做工时统计？ 版本制交付、节点驱动，不做固定迭代、不搞工时——看单数百分比就够了，里程碑清单就是发布清单（§4.4）。
3

合码前：核需求流 checklist

Developer 提 MR 时，描述里应该带着四项自查 checklist。你合码前除了看代码 diff 和 CI 绿，还要核这四项（§5.1）：

  • ☑ 关联需求单号——写了 Closes #单号（默认路径：合入即自动关单）还是只引用 #单号（需外部验收：合入后进待验证，你来手关）
  • ☑ 选定里程碑——这个版本要收的需求
  • ☑ CI 全绿
  • ☑ 自测通过
🔍 无单不开发（三无制度第一条，§7.1） 任何改动（需求、缺陷、现场修复）先有单，commit 必须能追到一张 issue——追不到单的 MR 不合入。这是需求流与代码流之间的焊点。

典型任务流：一次发布的全流程

1

评审 MR

MR 页切到 Changes 逐行看：批准记录在顶部，流水线状态在中部，合入信息在下方。有问题就在对应行内评论，Developer 修完会自动更新；看完没问题，点 Approve。

2

合入

点 Merge 按钮合入，main 流水线随即自动触发。

🔍 为什么 Developer 不能自己合？ 评审与合入分离是代码质量的最低保障（§4.3）——改代码的人不给自己的改动放行，守门人必须在场。
3

打 tag

main 流水线绿了、决定发版时，在本地打一个带说明的标注 tag 并推送：

$ git checkout main && git pull
$ git tag -a v0.2.0-field -m "现场验证版"
$ git push origin v0.2.0-field
4

等 tag 流水线

tag 推上去后自动触发 tag 流水线：先跑 build 产出制品，跑完后停在 promote-release 手动关卡（⏸ 等人按）。

5

手动批准晋升

确认 build 绿了，点 promote-release 的 ▶ Play，制品才从构建区晋升进发布区。

🔍 为什么晋升要手动？ 发布永远是人的决定，不是自动的（§6.3）——build 可以自动，但"这个版本要不要发出去"必须有人签字。
6

建 Release

左侧 Deploy → Releases → New release，选中刚打的 tag，把晋升出来的 .bin 与 manifest.json 附上——现场驻场同事就是从这个页面下载制品的。

🔍 产物三去向（二阶段新增，§6.4） .bin 与 manifest 进 GitLab Release（不变）；但容器镜像另有归宿——CI 构建的镜像推 Harbor 的 frm-ci 项目，模型权重推 MinIO 的 training-output 桶。后两者各有自己的 tag/指针，不挤在 Release 里。
7

核对追溯链

发完最后一眼：manifest.commit = main HEAD = tag commit = MR 合入 commit，四方一致才可放行（§6.3）。核对方法——Release 页 manifest 的 commit 字段 vs 仓库 main 页顶部 SHA。

二阶段多了两类产物，追溯链各自延伸：镜像核对 Harbor frm-ci 里的 tag→commit；模型权重核对 MinIO training-output 里 manifest 的 s3 指针→commit。三方各自能追到同一 commit，才算齐（§6.4）。

🔍 为什么必须四方一致？ 追溯链上任何一个环节对不上，就意味着现场拿到的制品和仓库里的代码不是同一份——出了问题查不到根，这是发布责任的红线（§6.3）。

常见报错自救

💡 Merge 按钮灰着，提示 conflicts 说明特性分支落后于 main，让分支先合入最新 main 再推： 
$ git fetch && git checkout feat/xxx && git merge origin/main
$ git push
解决冲突后 push，MR 自动更新。
💡 tag 打错了想删 git push origin :refs/tags/vX.Y.Z + GitLab 页面删 tag；已对外发布的 tag 不删，追加 -fix 新 tag。

红线清单

🚫 无单不开发——不合入追不到单的 MR MR 必须关联需求单号（Closes 或引用），追不到单的改动不合入（需求流设计 §7.1 三无制度）。
🚫 无里程碑不发布——tag/Release 必须挂里程碑 发版前确认 tag 所属里程碑已选定——无里程碑的版本不算数（需求流设计 §7.1）。
🚫 不合没有任何评审记录的"自己批自己" Owner 的 MR 同样要有第二双眼睛，评审与合入分离对守门人自己也成立（§4.3）。
🚫 发布产物必须来自 CI 构建区 本机编译的版本永远不发给现场（§5.4）——没有流水线和 manifest 背书的制品无法追溯。
🚫 tag 命名一旦对外，不复用不修改 现场按 tag 报障、按 tag 回溯，一个 tag 永远只指向一份制品（§6.3）。
