开发工程师上手指南

拉代码 → 建分支 → 改码 → push → 建 MR → 等 CI 绿

Developer

你是谁

你是本组的开发成员，在 GitLab 里的角色是 Developer：日常就是写代码、提 MR。典型一天：早上拉一把最新代码，从 main 建一条特性分支，改码提交 push，建一个 MR，然后等 CI 跑绿——绿了叫 Owner 来评审合入，红了自己修。

你能做什么 / 不能做什么

能 ✅不能 ❌
push 自己的特性分支直接 push main（系统直接拒绝）
建 MR、评论、修改到通过合入 MR（Owner 做）
触发并查看自己的流水线改保护分支设置、改成员权限

典型任务流：一次改动的全流程

1

找到并 clone 仓库

从 群组 → intel_excavator 进入你所在的产品域子组（如 autonomy），找到自己的仓库，用页面上给的 clone 地址拉到本地。

$ git clone http://gitlab.internal/intel_excavator/autonomy/perception.git
$ cd perception
🔍 哪天要建新仓库？先过"建仓三问" 仓库的位置和归属不是随手定的：① 哪个域？只能建在六个产品域子组里；跨域的体系设施有专门去处——CI 模板/规范进 platform，需求/缺陷进顶层 intake，两个都不属任何产品域。② Owner 是谁？一仓库 1–2 名 Maintainer，建仓时就要点名认领。③ 说得清用途吗？README 写齐用途/Owner/依赖、能编译——说不清用途的代码不入库。
2

从最新 main 建特性分支

分支名规则：feat/xxx（新功能）或 fix/xxx（修 bug）。永远不要在 main 上直接改。

$ git checkout main && git pull && git checkout -b feat/load-align
🔍 为什么要用短生命周期的分支？ main 常绿、小步快合。分支活得越久，和 main 的差异越大，几个月后合不回去的代价远大于勤合入。
2b

红线预告：main 不能直推

"不能直接 push main"不是口头规矩，而是系统强制：main 是保护分支，push/merge 权限只给了 Maintainer，你以 Developer 身份推上去会被直接拒绝。

这个设置只有 Owner 能改（管理 → 设置 → 仓库 → 受保护分支）。所以别试直推，老实走 MR。

3

改码 → commit → push

$ git add -A && git commit -m "feat: 装车对位置信度阈值 0.85→0.80"
$ git push -u origin feat/load-align

push 完看回显：GitLab 会自动返回一条创建 MR 的链接，直接点它就能建 MR，不用去页面里翻。

4

建 MR

左侧 合并请求 → 新建合并请求 建一个新 MR。标题按仓库规范写清这次改了什么；描述里必须写三件事：改了什么、为什么、怎么验证——评审者第一眼看的就是这三行。

描述里再加两件：关联单号（默认写 Closes #单号——合入即自动关单；需外部验收的单只写 #单号 引用，不写 Closes）与选定里程碑。仓库的 MR 模板已带四项自查 checklist：☑ 关联单号 ☑ 里程碑 ☑ CI 全绿 ☑ 自测通过。

🔍 无单不开发（三无制度第一条） 任何改动（需求、缺陷、现场修复）先有单，commit 必须能追到一张 issue。上面这张"自动装车对位误拒率偏高"就是先在受理台（intel_excavator/intake）提单、分诊转入本仓的。你自己发现的 bug / 技术改进？同样先去受理台提单，再开工——MR 描述里的 Closes 就是把"做了什么"和"为什么做"焊在一起的焊点。
5

等 CI，读结果

MR 页内嵌流水线：每次 push 到这条分支都会自动跑一遍密钥扫描、取数、训练。绿了等评审；红了点开对应 job 看日志，最后几十行通常就是原因。

🔍 你的算法流水线替你做什么 算法仓的流水线是 scan→data→build→publish：从 MinIO 取数据集（manifest 指针 + sha256 校验）→ 训练 → 把模型权重推回 MinIO。固件仓的流水线则是构建容器镜像推 Harbor。但你的操作不变：push 完等绿，红了点 job 看日志。
6

修到绿，等 Owner 合入

CI 红了或评审有意见：改完直接 push 新 commit 到同一分支，MR 会自动更新，不需要关掉重建。全绿 + 评审通过后，等 Owner 合入。

常见报错自救

💡 push 被拒：You are not allowed to push code to protected branches remote: GitLab: You are not allowed to push code to protected branches. → 说明你在推 main。回到自己的特性分支：git switch -c feat/xxx 再推。
💡 流水线直接 failed 且 0 个 job 日志含 Project 'intel_excavator/platform/ci-templates' not found or access denied → 你对 platform 组无读权限，找平台组给你加 Reporter。
💡 流水线红了怎么排查 job → 跟踪（Trace）看最后 30 行 → 本地复跑同命令 → git commit --allow-empty -m "ci: retry" 触发新流水线。注意：retry 不重新解析模板，改模板后必须触发新流水线。

红线清单

🚫 无单不开发 任何改动先有单（需求 / 缺陷 / 任务），MR 必须关联单号——追不到单的改动不合入。
🚫 不上传任何明文密钥 / 密码 CI 第一条 job 会跑 gitleaks 扫描，扫到即失败。
🚫 不对共享分支用 git push -f 强推会覆盖别人的提交历史，共享分支上永远禁止。
🚫 不把数据集 / 模型权重塞进 git git 只存 manifest 指针，大文件走 MinIO；发布产物只能来自 CI。
