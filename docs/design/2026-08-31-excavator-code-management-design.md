# 智能挖机项目统一代码管理体系设计

- 日期：2026-08-31
- 状态：已按三部分重组；2026-09-08 全文精简为正式文档风格，待逐节评审
- 定位：供团队内部评审、干系人沟通与分阶段实施使用

## 方案结构

现状：代码管控缺乏约束，部分代码仅存于个别成员的个人电脑。团队宁可不用集团 DevOps、也不安装 DLP，说明外部依赖不可控是现实约束。因此方案分三部分，各自独立推进：

- **第一部分 基础使用**：仅依赖机房服务器，无需外部谈判即可落地，解决代码散落与版本混乱，是团队立即可获得的价值。
- **第二部分 集成 DLP**：与集团安全部门协商，解决数据泄漏与合规问题；进度不影响第一部分。
- **第三部分 接入集团 DevOps 设施**：长期对接集团域账号与托管平台；当前信息不足，仅保留框架。

第一部分的投入在后两部分落地时均可保留：仓库结构、CI 配置、权限模型全部可迁移。

# 第一部分 基础使用

## 1. 现状与问题

当前最严重的问题是**单点丢失**：电脑损坏或人员离职即导致代码永久丢失。更普遍的是**版本混乱**：同一份代码谁持有最新版、改了什么、能否编译，无人能说清。代码托管位置、修改权限、问题责任人，均无制度约束。

目标：利用机房现有服务器搭建统一的代码管理体系，覆盖托管、评审、CI 流水线与驻场调试支持，优先解决"代码不再散落"。

## 2. 平台选型：自建 GitLab CE

在机房自建 **GitLab CE** 作为一体化平台，代码托管、权限、MR 评审、CI、镜像库、制品库合并于一个系统。选型理由：GitLab CE 是国内制造业研发中心私有化部署的事实标准，单系统覆盖全部功能，可支撑 50+ 人多团队，无需在多套系统间切换。

备选方案 Gitea + Jenkins + Harbor：组件轻量，但权限、账号、审计分散在三套系统中，维护成本高，且 Jenkins 易退化为新的个人黑盒。适用于 10 人以下团队，本项目不适用。

**许可说明**：CE 为 MIT 协议，商用免费，自建实例无用户数与 CI 分钟数限制；"5 用户上限"是 GitLab.com 云服务免费版的限制，与自建无关。CE 缺少以下付费（Premium）功能，均有替代：

- MR 审批规则（强制 N 人批准、CODEOWNERS）：以保护分支强制 MR 合入 + 制度约定批准人数替代；
- 推送拦截（密钥、文件类型）：以 CI 首条任务执行 gitleaks 扫描替代；
- 审计事件流：以基础日志定期归档替代；
- LDAP 分组同步：CE 原生支持 LDAP 登录认证，分组手动维护（域账号接入见第三部分）。

策略：CE 先落地；待审批硬约束成为实际痛点、或集团审计提出要求时再购买 license 升级，无需重装。实施时安装 `gitlab-ee` 包但不注入 license，按免费功能运行，购买后可直接升级。亦可评估极狐 GitLab（官方中国发行版，本地支持与合规更便利）。

集团已有托管平台，但能力边界与响应速度不明，第一部分不依赖；摸底属第三部分内容。

## 3. 仓库、分支与权限

仓库按产品域组织——团队会重组，产品域相对稳定：

```
excavator/                      # 顶层 group（智能挖机项目）
├── firmware/                   # 控制固件（MCU/PLC/控制器）
├── autonomy/                   # 算法（感知/规控/定位，含模型与训练代码）
├── vehicle/                    # 车载软件（控制器应用、座舱 HMI）
├── cloud/                      # 云端平台（监控、调度后台）
├── app/                        # 移动端
└── platform/                   # 平台工程（CI 模板、runner 配置、部署脚本、规范文档）
```

子组内按组件建仓库（如 `firmware/hydraulic-controller`、`autonomy/perception`），**每个仓库指定一名明确的 Owner**。`platform/` 是本体系的"宪法"：CI 模板与规范文档全部版本化，规则修改必须走 MR 评审，不允许口头变更。

分支模型为 **trunk-based 简化版**：`main` 常绿 + 短命特性分支 + MR 合入；固件等发布周期长的仓库允许保留 `release/x.y` 维护分支。**直接 push `main` 由系统禁止**（保护分支），必须走 MR。

权限仅使用 GitLab 五级中的三级：

| 角色 | 权限 | 授予对象 |
|---|---|---|
| Guest/Reporter | 只读 | 跨组查阅者、外部协作者 |
| Developer | push 分支、建 MR | 本组开发成员 |
| Maintainer | 合 MR、管保护分支 | 每仓库 1–2 名 Owner |

**禁止任何个人持有顶层 group 的 Owner 角色**——Owner 仅属于平台维护账号，避免产生新的代码诸侯。

账号采用**本地账号**过渡：平台维护人手工建号、离职手工停用；root 本地账号保留为 break-glass 应急通道（密码受控保管，是本地账号唯一的特权例外）。本地账号依赖人工操作，必有遗漏，故仅为过渡方案——接入集团域账号（第三部分）后，由域账号生命周期自动管理，该漏洞即消除。过渡期内平台维护人定期盘点账号清单。

存量代码设置入库门槛：能编译、README 写明用途/Owner/依赖。**用途说不清的代码不入库**——宁可在迁移中淘汰，也不将个人电脑上的无序状态带入新体系。

## 4. CI 与制品管理

CI 目标：代码推送后，编译、检查、测试、出制品自动完成，无需人工值守，且**同一份代码从构建到烧入挖机全程可追溯**。

**Runner 按任务类型分池**，GitLab 主机仅负责调度：

| Runner 池 | 任务 | 硬件 |
|---|---|---|
| `fw-build` | 固件交叉编译、静态检查 | 机房虚机 ×2 |
| `algo-gpu` | 模型训练、仿真回放测试 | GPU 服务器 |
| `veh-build` | 车载 C++/Qt 构建打包 | 机房虚机 ×1 |
| `cloud-deploy` | 云端构建部署 | 机房虚机 ×1 |
| `hil-rig` | 手动触发的硬件在环测试 | 接台架的实体机 |

**流水线分三层**：通用层——`platform/ci-templates` 提供固件/算法/车载/云端四套模板，新仓库复制即用，规则集中管理；仓库层——各仓库覆盖细节配置，但必须 include 通用层，未 include 的流水线 MR 不予合入（制度与流水线自检双重约束）；下游层——固件与算法专有，MCU 产物须经固件签名、模型产物须经模型评测，通过后进入发布流程。

**制品按流水线晋升**：CI 构建 → 测试环境验证 → 手动批准晋升 → 生产发布。发布使用 GitLab tag + release，每个发布固件均可回答：源码 commit、构建环境（镜像 digest）、签名人、构建时间。

**对外交付的制品必须由 CI 构建，禁止以本地编译替代。** 本地编译的产物无法回答"源码是什么、谁构建的"，现场机器运行内容将成为黑箱。每个发布物内嵌 `manifest.json`（版本号、commit、构建时间、依赖清单），现场维护人员据此即可识别机器运行内容。

**存储按产物形态划分**：容器镜像（CI 基础镜像、CUDA 训练环境）存 Harbor；二进制通用包（Conan/npm/Maven）使用 GitLab 内置 package registry；固件 .bin 与部署包挂 GitLab Release 附件；大文件（数据集、模型权重）不进 git，存 MinIO 对象存储，git 中仅保留清单与指针。Harbor、MinIO、Nexus 在第一部分即部署，保证 CI 拉包可靠与驻场离线可用。

**密钥管理**：密钥走 GitLab 受保护变量；部署私钥与固件签名密钥存放于受控主机（CE 无签名集成，以独立脚本 + 受控主机或 HSM 实现，成本可控），流水线不接触明文密钥。仓库内禁止出现明文密钥——CE 无推送拦截，以 CI 首条任务执行 gitleaks 补足。

## 5. 驻场支持

驻场是本体系直接服务的核心场景。原则：**离线为基线、有网为加速**，流程不依赖现场网络。

**出场前**在公司完成准备：`git pull` 同步代码；从 GitLab Release 下载本次任务相关的已签名制品，按目标机器版本打包；对照 `platform/` 仓库的出场 checklist 核对代码、制品、工具链版本与联系人。

**现场三类工作对应三条通道**：

- **调试、刷固件**：使用预构建签名制品并以 `manifest.json` 核对；**现场不编译**，需要新版本走第二条通道。
- **改代码**（bug 修复、参数调整）：本地 commit，有网即 push 走 MR → CI 构建 → 下载刷入。改动**必须**以 commit 形式回到中心仓库——这是防止代码重新散落回个人电脑的硬规则。
- **取数**（日志、传感器数据）：数据进入 MinIO 投放区，现场可连则直传，不可连则回公司后上传。数据向内、代码仅经 git 向外，流向单一，审计简单。

**现场改码的现实困境**：改了代码、现场断网、机器等待验证。解法是区分本地验证与正式构建：

1. 允许在笔记本本地编译做临时验证；
2. 刷入机器的正式版本必须来自 CI 签名制品；网络恢复后 push，由 CI 出包，远程指导刷入；
3. 极端情况（断网且机器急等）允许刷入本地临时包，但回公司后 24 小时内必须补齐 MR 与正式构建，逾期按违规处理。

应急通道保留，但全程留痕可查。须向团队明确：临时包仅用于应急，不是工作方式。

**网络条件好的现场**可经 VPN 回内网直接使用 GitLab，体验与公司内一致。现场 U 盘与移动硬盘按集团外发策略审批、使用加密盘。与挖机 ECU 的物理连接（CAN/以太网调试）为纯本地操作，无合规冲突。

## 6. 实施阶段

| 阶段 | 内容 | 完成标志 | 周期 |
|---|---|---|---|
| 0 盘点与共识 | 全员盘点存量代码（内容、依赖、是否在用），产出《存量代码台账》；设计文档送各团队负责人评审，评审过程即干系人识别过程 | 台账成稿，反对意见逐条归档 | 2–4 周 |
| 0.5 服务器资源 | 与集团 IT 协商机房虚机/物理机，与阶段 0 并行 | 服务器资源有书面结论 | 并行 |
| 1 基础设施 | 机房部署 GitLab（`gitlab-ee` 免费运行）+ runner 虚机 ×2 + Harbor/Nexus 代理 + MinIO | 本地账号能登录、能建 MR、示例流水线全绿 | 2–3 周 |
| 2 收编存量代码 | 按"说得清用途才入库"分批迁移，指定 Owner、补 README、跑通 CI | **个人电脑不再是代码权威副本**（正式宣布的里程碑） | 4–8 周 |
| 3 CI/CD 深化 | 固件签名、模型评测、HIL 台架接入、OTA manifest 机制 | 近三个月发布的每个固件都能回答"源码是什么、谁构建、谁签名" | 持续 |

LDAP 域账号接入属第三部分，不阻塞本部分任何阶段。

## 7. 风险与应对

| 风险 | 应对 |
|---|---|
| **人的抵触（最大风险）** | 迁移期只立新规、不究旧账（历史不追究，从今往后按新规则）；向成员说明收益（设备损坏代码不丢、CI 自动执行测试）；Owner 角色给予充分认可 |
| 平台维护断档 | 指定 1 名兼职平台维护人（发起人先行，规划交接）；无人维护的单实例 GitLab 两年内必然退化为无序 |
| 工程师将代码粘贴进公有云 AI 工具 | 制度明确：仅使用集团批准或私有化部署的 AI 工具；纳入安全培训 |
| 本地账号过渡期漏停 | 平台维护人定期盘点账号清单；推进第三部分域账号接入以消除该风险 |

## 8. 备份与容灾

- GitLab 原生全量备份（配置 + 仓库 + 数据库）每日一次，保留异地/离线副本；
- Harbor、MinIO 各自配置快照；
- **MinIO 数据按资产备份**：数据集、模型权重、现场采集数据是资产而非缓存，其中现场采集数据**不可再生**——按数据分级制定保留与备份策略，容灾等级与代码一致。数据丢失同样回到"单点丢失"这一本方案要解决的原点问题；
- **恢复演练每半年一次**——未经演练的备份等同于没有备份。

# 第二部分 集成 DLP

## 1. 目标与边界

第一部分解决代码散落与版本混乱，未涉及数据泄漏。代码存于工程师笔记本违反集团防泄漏规定，DLP 合规压力持续存在。第二部分在第一部分基线上增加合规层，与集团安全部门协商解决。

边界：本部分谈判失败或延期，均不影响第一部分已落地的内容。

## 2. 技术前提：透明加密与边界

集团 DLP 为 **IPguard，透明加解密类**——对 CI/CD 影响最大的形态。机制：终端磁盘文件加密，授信进程读取为明文。因此**加密边界始终在终端**：git 读出明文，push 走 HTTPS/SSH 传输明文，GitLab 服务器落盘为明文仓库，未装 agent 的 Runner 检出构建不受影响。

这是本部分方案的物理基础，也是向安全部门说明"构建区不装 agent 不会导致泄漏"的核心论据。

## 3. 两区模型

| 区域 | DLP Agent | 网络位置 | 部署内容 |
|---|---|---|---|
| 办公研发区 | 安装（透明加解密） | 公司办公网 | 工程师笔记本/工作站 |
| 机房构建区 | **豁免** | 隔离网段，只通内网 | GitLab、Runner、GPU、镜像/制品库 |

## 4. 谈判要点

1. **构建区豁免**：GitLab/Runner/制品库服务器不装、或仅装审计模式的 DLP agent。否则构建产物被加密、Docker 分层缓存失效、CI 缓存损坏，流水线无法运行。
2. **终端进程授信**：开发机上的 git、ssh、IDE 进程加入授信白名单。git 未授信是此类 DLP 最典型的故障：仓库文件被二次加密，push 上传的是密文，整仓污染。
3. **文件类型策略**：源码类扩展名加密；构建产物（.bin/.o/.img 等）不加密——产物要在大量未装 agent 的设备（挖机 ECU、现场控制器）上运行，加密即不可用。

授信配置细节（进程白名单粒度、策略格式）需取得集团 DLP 产品官方文档后确认，列为行动项。

## 5. 交换条件

谈判是交换而非对抗。向安全部门提供：

- 构建区**无外网直连**：pip/npm/docker 拉包一律经内网 Nexus/Harbor 代理，出口收敛、日志可查（第一部分已部署 Harbor/MinIO，此处纳入"出口收敛"的合规叙事）；
- 机房门禁 + 运维操作审计；
- GitLab 审计日志定期归档，安全部门可随时调阅；
- 驻场终端照常全量安装 DLP——**现场笔记本遗失时，磁盘上的代码仍为密文**。

## 6. 一条规则的两个动机

第一部分规定"对外制品必须由 CI 在构建区构建，禁止本地编译"。本部分补充第二个动机：构建区豁免 agent 后，产物不受终端透明加密影响，可用性有保障——这是"产物不加密"策略的执行保障。

两个动机相互独立：第一部分要版本可追溯，本部分要产物可用。即使 DLP 谈判未成，制品仍必须走 CI。

## 7. 上线验证

开发机 DLP 铺开时执行授信验证清单：git push/pull、IDE 打开仓库、CI 触发逐项验证；发现污染立即停止并走应急流程；清单全绿方可视为完成。

此步可与第一部分阶段 2（收编存量代码）并行，不构成阻塞——DLP 故障只影响开发机侧，机房 CI 与仓库不受影响。

## 8. 降级预案

若安全部门拒绝构建区豁免，可降级：

- **降级一**：构建区安装 agent，策略设为仅审计；
- **降级二**：构建任务回退到装有 agent 的虚机运行，接受性能损失。

两种预案均可接受，谈判失败不是死局。

> 本部分工期自谈判取得书面结论起算，不提前对外承诺日期。谈判期间第一部分照常推进。

# 第三部分 接入集团 DevOps 设施

## 1. 总体策略

集团有域账号体系，也可能有托管平台，能力边界与响应速度均不明。策略为**自下而上、带方案推动**：第一部分自建 GitLab 先落地运行，通过推进过程中收集的反对意见识别需配合的干系人，再逐步对接集团设施。

核心约束：**第一部分的投入不作废**——仓库结构、CI 配置、权限模型全部可迁移：或整体迁移至集团平台，或仅将本地账号替换为域账号，代码与流程不变。

## 2. 域账号接入

第一部分的本地账号仅为过渡（手工建停、依赖人工、必有遗漏）。接通集团 LDAP 后，账号由域账号生命周期自动管理，该漏洞消除。

GitLab 对接集团 LDAP（CE 原生支持登录认证），**禁止本地建账号**；root 本地账号保留为 break-glass 应急通道，是唯一例外。配置 `user_filter` 限定自动建号范围（不配置则全集团域账号均可登录）。

CE 开箱能力边界与补齐方式：

| 环节 | 自动程度 | 补齐方式 |
|---|---|---|
| 入职自动有账号 | ✅ 域账号首次登录自动建号 | 无需操作 |
| 入职自动有权限 | ⚠️ 手动加组（CE 无分组同步） | Maintainer 操作，或升 Premium |
| 离职：登录失效 | ✅ 域账号禁用后登录/密码认证立即失败 | 取决于 IT 禁用时效 |
| 离职：存量访问（SSH key、令牌、会话） | ❌ 不自动失效 | **定时脚本比对 AD 禁用名单 → 调 API 封禁账号** |

迁移动作：本地账号与域账号建立映射；用户首次以域账号登录后，停用对应本地账号；封禁脚本列入本阶段实施项。前置申请：LDAPS（636）+ 服务账号（bind DN），向集团 IT 提出。
