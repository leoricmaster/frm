# 智能挖机项目统一代码管理体系设计

- 日期：2026-08-31
- 状态：结构已按三部分重组，待重新逐节评审
- 定位：供团队内部评审、干系人沟通与分阶段实施使用

## 这个方案分三部分

智能挖机项目的代码管控现在比较随意，部分代码只存在个别成员的个人电脑上。要解决这个问题，但不一定要一次性把所有事都谈拢——团队现在宁可不用集团 DevOps、也不装 DLP，本身就说明有些外部依赖既慢又不一定成。

所以方案分三部分，能各走各的：

- **第一部分 基础使用**：只用机房服务器，零外部谈判就能落地。让代码不再散在个人电脑上、版本能统一管起来。这是团队立刻能拿到的价值。
- **第二部分 集成 DLP**：跟集团安全部门谈，把数据泄漏和合规问题解决掉。不谈也不影响第一部分。
- **第三部分 接入集团 DevOps 设施**：长远跟集团的域账号、托管平台打通。现在信息不多，先留框架。

第一部分的投入在后面两部分场景下都不作废——仓库怎么组织、CI 怎么配、权限怎么设，全部能带走或迁移。

# 第一部分 基础使用

## 1. 代码散在个人电脑上

智能挖机项目团队现在最大的问题是**单点丢失**：电脑一坏、人一走，代码永久没了。比这更普遍的是**版本混乱**：同一份代码谁手上的最新、改了什么、还能不能编译，没人说得清。代码托管在哪、谁有权限改、出了问题找谁，全靠个人自觉。

目标是用机房里已有的服务器，搭一套统一的代码管理体系——托管、评审、CI 流水线、驻场调试支持一站覆盖。先把"代码不再散落"这件事解决掉。

## 2. 用机房服务器搭一个统一平台

在机房自建一个 **GitLab CE** 作为一体化平台：代码托管、权限、MR 评审、CI、镜像库、制品库都在一个系统里。选 GitLab CE 是因为它是国内制造业研发中心私有化部署的事实标准，一个系统管完所有事，50+ 人多团队也撑得住，不用在好几套系统之间来回切。

另一个候选是 Gitea + Jenkins + Harbor 拼装，组件轻，但权限、账号、审计分散在三套系统里维护成本太高，而且 Jenkins 容易演变成新的个人黑盒。适合 10 人以下，这个团队用不合适。

**CE 是 MIT 开源协议，商用免费，用户数和 CI 分钟数都不限。** 网上常说的"5 用户上限"那是 GitLab.com 云服务免费版的限制，跟自建实例无关。CE 确实缺几个付费（Premium）功能，但有替代：

- **MR 审批规则**（强制 N 人批准、CODEOWNERS 强制评审）——靠保护分支强制 MR 合入 + 制度约定批准人数顶上；
- **推送拦截**（拦截密钥、文件类型）——CI 第一条任务跑 gitleaks 密钥扫描顶上；
- **审计事件流**——基础日志定期归档；
- **LDAP 分组同步**——LDAP 登录认证 CE 本来就有，分组手动维护（接了域账号再说，见第三部分）。

策略是 CE 先落地，等审批硬约束真的变成痛点、或者集团审计提出要求，再买 license 升级，不用重装。实施上装 `gitlab-ee` 包但不注入 license，按免费功能跑，将来买了直接就升级了。国内也可以问问极狐 GitLab，官方中国发行版，本地支持和合规叙事更顺。

集团那边其实也有托管平台，但能力边界和响应速度都不清楚。这里先不依赖它，等第一部分站稳了再摸底——那是第三部分的事。

## 3. 代码怎么放、谁有权动

仓库按产品域组织，因为团队会重组但产品域相对稳定：

```
excavator/                      # 顶层 group（智能挖机项目）
├── firmware/                   # 控制固件（MCU/PLC/控制器）
├── autonomy/                   # 算法（感知/规控/定位，含模型与训练代码）
├── vehicle/                    # 车载软件（控制器应用、座舱 HMI）
├── cloud/                      # 云端平台（监控、调度后台）
├── app/                        # 移动端
└── platform/                   # 平台工程（CI 模板、runner 配置、部署脚本、规范文档）
```

每个子组里按组件建仓库（比如 `firmware/hydraulic-controller`、`autonomy/perception`），**一个仓库一个明确的 Owner**。`platform/` 是这套体系自己的"宪法"：CI 模板、规范文档都版本化在里面，规则要改走 MR 评审，不是谁口头说了算。

分支统一用 **trunk-based 简化版**：`main` 常绿 + 短命特性分支 + MR 合入。固件这类发布周期长的仓库可以留 `release/x.y` 维护分支。**直接 push `main` 被系统禁止**，必须走 MR。

权限只用 GitLab 五级里的三级：

| 角色 | 权限 | 给谁 |
|---|---|---|
| Guest/Reporter | 只读 | 跨组查阅的人、外部协作者 |
| Developer | push 分支、建 MR | 本组开发 |
| Maintainer | 合 MR、管保护分支 | 每仓库 1–2 名 Owner |

**任何个人都不许拿顶层 group 的 Owner 角色**——Owner 只属于平台维护账号，免得出现"新的代码诸侯"。

账号这块先用**本地账号**：平台维护人手工建号、离职手工停用，root 本地账号留着当 break-glass 应急通道（密码受控保管，是本地账号唯一的特权例外）。本地账号靠人记得开关，必然会漏，所以这只是过渡——等接通集团域账号（第三部分），本地账号迁过去、由域账号的生命周期自动管，手工漏停的漏洞就消了。过渡期间平台维护人定期盘点账号清单，别让废弃账号堆着。

存量代码不是一股脑全搬进来。入仓库有个门槛：能编译、有 README 写清用途/Owner/依赖。**说不清用途的代码不入库**——宁可在迁移里淘汰掉，也不把个人电脑里的混沌原样搬进新体系。

## 4. 让 CI 替你跑

CI 要做到的是：代码一推上去，编译、检查、测试、出制品这些事自动完成，不用人盯着，而且**同一份代码从构建到烧进挖机全程能追溯**。

**Runner 按活分池**，GitLab 主机只管调度不干重活：

| Runner 池 | 干什么 | 硬件 |
|---|---|---|
| `fw-build` | 固件交叉编译、静态检查 | 机房虚机 ×2 |
| `algo-gpu` | 模型训练、仿真回放测试 | GPU 服务器 |
| `veh-build` | 车载 C++/Qt 构建打包 | 机房虚机 ×1 |
| `cloud-deploy` | 云端构建部署 | 机房虚机 ×1 |
| `hil-rig` | 手动触发的硬件在环测试 | 接台架的实体机 |

**流水线分三层**。通用层在 `platform/ci-templates` 里提供固件/算法/车载/云端四套模板，新仓库复制就能用，规则集中管。仓库层各自 override 细节，但必须 include 通用层——不 include 的流水线 MR 不让合，制度和流水线自检双保险。固件和算法还有个下游层：MCU 产物要过固件签名，模型产物要过模型评测，过了才进发布流程。

**制品晋升走流水**：CI 构建 → 测试环境验证 → 手动批准晋升 → 生产发布。发布用 GitLab 的 tag + release，每个发布固件都能回答：源码是哪个 commit、用的什么构建环境（镜像 digest）、谁签的、什么时候建的。

**对外交付的制品必须由 CI 构建，不能在个人电脑上编译一个凑合。** 这不只是为了规范——本地编译的包根本回答不了"源码是什么、谁构建的"，现场机器上跑的是什么就成了黑箱。每个发布物里内嵌一个 `manifest.json`（版本号、commit、构建时间、依赖清单），现场维护人员一查就知道机器上跑的是啥，直接服务驻场场景。

**存储按形态分家**：容器镜像（CI 基础镜像、CUDA 训练环境）放 Harbor；二进制通用包（Conan/npm/Maven）用 GitLab 内置的 package registry；固件 .bin 和部署包挂 GitLab Release 附件；大文件（数据集、模型权重）不进 git，放 MinIO 对象存储，git 里只存清单和指针。Harbor、MinIO、Nexus 在第一部分就部署好，CI 拉包可靠、驻场离线也用得上。

**密钥**走 GitLab 受保护变量，部署私钥和固件签名密钥放在受控主机上（CE 没有签名集成，用独立小脚本 + 受控主机或 HSM，成本可控），流水线碰不到明文密钥。仓库里不许出现任何明文密钥——CE 没有推送拦截，所以 CI 第一条任务跑 gitleaks 把这个缺口补上。

## 5. 驻场：离线也能干活

驻场是这套体系要直接服务的真实场景。原则是**离线为基线、有网为加速**——流程不赌现场有网。

**出场前**在公司里把东西备齐：`git pull` 同步代码，从 GitLab Release 下载这次任务相关的已签名制品，按目标机器的版本打包好。对照 `platform/` 仓库里的出场 checklist 走一遍：代码、制品、工具链版本、联系人都核对到。

**现场三类工作走三条通道**：

- **调试、刷固件**——用预构建的签名制品 + `manifest.json` 核对。**现场永远不编译**，要新版本走第二条。
- **改代码**（bug 修复、参数调整）——笔记本上本地 commit，有网就 push 出去走 MR → CI 构建 → 下载刷入。改动**必须**以 commit 形式回中心仓库，这是防止代码重新散落回个人电脑的硬规则。
- **取数**（日志、传感器数据）——数据进 MinIO 的投放区，现场能连就直传，不能连就回公司再传。数据往内流、代码往外只走 git，方向单一，审计简单。

**现场改码的现实困境**：改了一行代码，现场没网，机器等着验证。解法是把本地验证和正式构建分开——

1. 允许在笔记本上本地编译做临时验证；
2. 但刷上机器的正式版本必须来自 CI 签名制品，网络恢复后 push 出去由 CI 出包，远程指导刷入；
3. 极端情况（断网 + 机器急等）允许刷本地临时包，但回公司 24 小时内必须补齐 MR 和正式构建，否则按违规处理。

应急缝留着，但缝有账可查。要跟团队讲清楚：临时包是救火用的，不是工作方式。

**条件好的现场**可以 VPN 回内网直接用 GitLab，体验跟公司内一样。现场 U 盘和移动硬盘按集团外发策略走审批加密盘。跟挖机 ECU 的物理连接（CAN/以太网调试）是纯本地的，没什么合规冲突。

## 6. 怎么一步步落地

| 阶段 | 做什么 | 完成的标志 | 周期 |
|---|---|---|---|
| 0 盘点与共识 | 全员存量代码盘点（谁有什么、依赖什么、还在不在用），产出《存量代码台账》；设计文档送各团队负责人评审——评审过程本身就是识别干系人的过程 | 台账成稿，反对意见逐条归档 | 2–4 周 |
| 0.5 服务器资源 | 跟集团 IT 谈机房虚机/物理机，跟阶段 0 并行 | 服务器资源有书面结论 | 并行 |
| 1 基础设施 | 机房部署 GitLab（`gitlab-ee` 免费运行）+ runner 虚机 ×2 + Harbor/Nexus 代理 + MinIO | 本地账号能登录、能建 MR、示例流水线全绿 | 2–3 周 |
| 2 收编存量代码 | 按"说得清用途才入库"分批迁移，指定 Owner、补 README、跑通 CI | **个人电脑不再是代码权威副本所在地**（正式宣布的里程碑） | 4–8 周 |
| 3 CI/CD 深化 | 固件签名、模型评测、HIL 台架接入、OTA manifest 机制 | 近三个月发布的每个固件都能回答"源码是什么、谁构建、谁签名" | 持续 |

LDAP 域账号接通是第三部分的事，不卡这里任何阶段。

## 7. 风险

| 风险 | 怎么应对 |
|---|---|
| **人的抵触（最大风险）** | 迁移期间只立规则不追旧账（历史不追究，从今往后按新规则）；强调收益（电脑坏了代码还在、CI 替你跑测试）；Owner 角色给足荣誉感 |
| 平台维护断档 | 指定 1 名兼职平台维护人（发起人起手、规划交接）；没人照看的单实例 GitLab 两年内必然劣化回混沌 |
| 工程师把代码贴进公有云 AI 工具 | 制度明确：用集团批准的 AI 工具或私有化部署的，纳入安全培训 |
| 本地账号过渡期漏停号 | 平台维护人定期盘点账号清单；尽快推进第三部分接域账号消除这个风险 |

## 8. 备份

- GitLab 原生全量备份（配置 + 仓库 + 数据库）每天一次，留异地/离线副本；
- Harbor、MinIO 各自配快照；
- **MinIO 里的数据要按资产备份**：数据集、模型权重、现场采集数据不是缓存是资产，其中现场采集数据**不可再生**——按数据分级定保留和备份策略，跟代码同级容灾。数据丢了同样回到"单点丢失"这个本方案要解决的原始问题；
- **恢复演练每半年一次**——没演练过的备份等于没备份。

# 第二部分 集成 DLP

## 1. 为什么还要管 DLP

第一部分解决了代码散落和版本混乱，但没碰数据泄漏：代码在工程师笔记本上，违反集团防泄漏规定，DLP 合规压力一直在。第二部分在第一部分的基线上叠一层合规，跟集团安全部门把这件事谈下来。

关键是：这部分谈不拢、或者拖很久，都不影响第一部分已经落地的东西。

## 2. DLP 是透明加密，关键在边界

集团 DLP 是 **IPguard，透明加解密类**——这是对 CI/CD 影响最大的形态。它的工作方式是把终端磁盘上的文件加密，但授信进程读出来的是明文。所以代码的**加密边界始终在终端**：git 读出明文、push 走 HTTPS/SSH 传的也是明文，GitLab 服务器上落盘的是明文仓库，没装 agent 的 Runner 检出来构建完全正常。

这是后面整个方案的物理基础，也是跟安全部门解释方案时的核心论据：构建区不装 agent 不会让代码泄漏出去，因为加密只发生在终端磁盘上。

## 3. 两区：办公装、机房豁免

| 区域 | DLP Agent | 网络位置 | 放什么 |
|---|---|---|---|
| 办公研发区 | 装（透明加解密） | 公司办公网 | 工程师笔记本/工作站 |
| 机房构建区 | **豁免** | 隔离网段，只通内网 | GitLab、Runner、GPU、镜像/制品库 |

## 4. 跟安全部门谈三件事

1. **构建区豁免**：GitLab/Runner/制品库服务器不装、或只装审计模式的 DLP agent。否则构建产物被加密、Docker 分层缓存全失效、CI 缓存损坏，流水线根本跑不起来。
2. **终端进程授信**：开发机上的 git、ssh、IDE 进授信白名单。git 没授信是这类 DLP 最经典的故障——仓库文件被二次加密，push 上去的是密文垃圾，整个仓库污染。
3. **文件类型策略**：源码类扩展名加密；构建产物（.bin/.o/.img 这些）不加密——产物要在无数没装 agent 的设备（挖机 ECU、现场控制器）上跑，加密了等于产物没法用。

具体的授信配置（进程白名单粒度、策略格式）要等拿到集团 DLP 产品名后对着官方文档确认，这是个行动项。

## 5. 我们拿什么换

谈判是交换不是对抗。我们给安全部门的：

- 构建区**没有外网直连**，pip/npm/docker 拉包一律走内网 Nexus/Harbor 代理镜像，出口收敛、日志可查（第一部分已经把 Harbor/MinIO 部署好了，这里把它纳入"出口收敛"的合规叙事）；
- 机房门禁 + 运维操作审计；
- GitLab 审计日志定期归档，安全部门随时能调阅；
- 驻场终端照常全量装 DLP——**现场笔记本丢在工地上，硬盘上的代码是密文**。

## 6. 一条铁律的两面

第一部分定了"对外制品必须由 CI 在构建区构建，不许本地编译凑合"。这里补上它的另一半动机：构建区豁免了 agent，产物不会被终端透明加密，保证产物可用——这是谈判里"产物不加密"策略的执行保障。

一个规则，两个动机：第一部分要的是版本可追溯，这部分要的是产物可用。第一部分那个动机不依赖这里的谈判结果——就算 DLP 没谈成，制品照样得走 CI。

## 7. 铺开时怎么验证不翻车

开发机 DLP 铺开的时候，跑一个授信验证清单：git push/pull、IDE 打开仓库、CI 触发都过一遍。发现污染立刻停、走应急流程。清单全绿才算完。

这步可以跟第一部分的阶段 2（收编存量代码）重叠，但不卡第一部分——DLP 出问题只影响开发机侧，机房的 CI 和仓库不受影响。

## 8. 谈不拢也不是死局

如果安全部门拒绝构建区豁免：

- **降级一**：构建区装 agent，但策略降成只审计；
- **降级二**：构建任务回退到装了 agent 的虚机上跑，接受性能损失。

都能接受，不是死局。

> 这部分的工期从谈判拿到书面结论起算，不提前对外承诺日期。谈判期间第一部分照常推进。

# 第三部分 接入集团 DevOps 设施

## 1. 长远要和集团设施打通

集团有域账号体系，也可能有托管平台，但能力边界和响应速度现在都不清楚。推进策略是**自下而上带方案推动**：第一部分先把自建 GitLab 站稳，通过推进过程中听到的反对声音去识别要配合的干系人，再一点点往集团设施上靠。

核心是**第一部分的投入不作废**：仓库结构、CI 配置、权限模型全部能带走——要么整体迁移到集团平台，要么只是把账号从本地换成域账号，代码和流程都不动。

## 2. 先接域账号，替掉本地账号

第一部分用本地账号过渡（手工建号、手工停号，靠人记得，必然漏）。接通集团 LDAP 域账号后，这块由域账号生命周期自动管，漏洞就消了。

GitLab 对接集团 LDAP（CE 原生支持登录认证），**禁止本地建账号**，root 本地账号留作 break-glass 应急通道、是唯一例外。配 `user_filter` 限定能自动建号的范围（不配的话全集团域账号都能登录）。

CE 的开箱能力有边界，得知道哪里自动、哪里要补：

| 环节 | 自动程度 | 怎么补 |
|---|---|---|
| 入职自动有账号 | ✅ 域账号首次登录自动建号 | 不用操作 |
| 入职自动有权限 | ⚠️ 手动加组（CE 没分组同步） | Maintainer 操作，或升 Premium |
| 离职：登录失效 | ✅ 域账号禁用后登录/密码认证立即失败 | 看 IT 禁用时效 |
| 离职：存量访问（SSH key、令牌、会话） | ❌ 不自动失效 | **定时脚本比对 AD 禁用名单 → 调 API 封禁账号** |

迁移动作：本地账号 → 域账号做映射，用户首次用域账号登录后停掉对应的本地账号，封禁脚本列入这个阶段的实施项。前置申请是 LDAPS（636）+ 服务账号（bind DN），要找集团 IT 要。

## 3. 集团托管平台：先摸底再说

摸底集团是不是已经有代码托管平台。有的话评估两个选项：直接接入，还是按第一部分自建。评估看几个维度——能力边界（支不支持本方案要的仓库结构/CI/制品库）、响应速度、审批流程、迁移成本。

这部分信息现在不多，整体是框架预留。各阶段按集团侧条件成熟度择机推进，不卡第一、第二部分。摸底后把这部分补全。
