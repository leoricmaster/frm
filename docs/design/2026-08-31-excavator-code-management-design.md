# 智能挖机项目统一代码管理体系设计

- 日期：2026-08-31
- 状态：设计已与发起人逐节评审确认
- 定位：供团队内部评审、干系人沟通与分阶段实施使用

## 1. 背景与问题

智能挖机项目团队当前代码管控方式较为随意，部分代码仅存于个别成员个人电脑。存在两类风险：

1. **数据泄漏**：违反集团防泄漏规定，DLP 合规压力；
2. **单点丢失**：电脑损坏、人员流动即导致代码永久丢失——此风险 DLP 完全不覆盖，与合规同等重要。

目标：建立统一代码管理体系，覆盖代码托管、CI/CD 流水线、驻场人员调试开发支持，并在集团 DLP / VPN 管理框架内运行。

## 2. 约束与前提（已澄清）

| 项 | 现状 |
|---|---|
| 团队规模 | 50 人以上，多团队 |
| 代码栈 | 嵌入式/控制固件、算法（含 GPU）、车载/上位机软件、云端/App，四类并存 |
| 驻场网络 | 混合条件——部分现场无网/弱网，部分可 VPN 回公司 |
| 集团 DLP | 透明加解密类（对 CI/CD 构建影响最大的形态） |
| 硬件资源 | 机房服务器可用、GPU 资源可用 |
| 集团托管平台 | 不清楚是否已有、不知道该找谁；推进策略为**自下而上带方案推动**，通过反对声音识别需配合的干系人 |
| 推论 | 方案必须**自洽可独立落地**，同时预留接入集团设施的平滑迁移接口 |

## 3. 方案选型

### 3.1 候选与结论

- **方案 A：自建 GitLab CE 一体化平台（选定）**——代码托管、权限、MR 评审、CI、镜像库、制品库一站覆盖；国内制造业研发中心私有化部署的事实标准。
- 方案 B：Gitea + Jenkins + Harbor 拼装——组件轻量但权限/账号/审计分散在三套系统，50+ 人多团队维护成本过高，且 Jenkins 易演化成新的个人黑盒。适合 10 人以下，否决。
- 方案 C：接入集团设施——不作为独立方案，而是方案 A 的**预留演进路径**：GitLab 仓库可整体迁移，仓库结构、CI 配置、权限模型全部带走，A 的投入在 C 场景下不作废。

### 3.2 授权与费用边界

- CE 为 MIT 开源协议，**商用免费，自建实例用户数不限、CI 分钟数不限**（"5 用户上限"仅存在于 GitLab.com SaaS 免费版，与本方案无关）。
- CE 缺失的付费（Premium）功能及替代：

| 缺失功能 | 影响 | CE 下的替代 |
|---|---|---|
| MR 审批规则（强制 N 人批准、CODEOWNERS 强制评审） | 中 | 保护分支限 MR 合入（系统强制）+ 批准人数制度约定 |
| Push rules（推送拦截密钥/文件类型） | 低 | CI 首条任务跑 gitleaks 密钥扫描 |
| 审计事件流 | 低 | 基础日志定期归档 |
| SAML/LDAP 分组同步 | 低 | LDAP 认证 CE 即有，分组手动维护 |

- 策略：**CE 先行落地，审批硬约束成为真实痛点或集团审计提出要求时再升级**。
- 实施细节：安装 `gitlab-ee` 包但不注入 license（按免费功能运行），将来购买 license 即升级、无需重装。国内亦可询价极狐 GitLab（官方中国发行版，本地支持与合规叙事更顺）。

## 4. 仓库结构与权限规则

### 4.1 仓库结构

按产品域组织（团队会重组，产品域相对稳定）：

```
excavator/                      # 顶层 group（智能挖机项目）
├── firmware/                   # 控制固件（MCU/PLC/控制器）
├── autonomy/                   # 算法（感知/规控/定位，含模型与训练代码）
├── vehicle/                    # 车载软件（控制器应用、座舱 HMI）
├── cloud/                      # 云端平台（监控、调度后台）
├── app/                        # 移动端
└── platform/                   # 平台工程（CI 模板、runner 配置、部署脚本、规范文档）
```

- 每个子 group 内按组件建仓库（如 `firmware/hydraulic-controller`、`autonomy/perception`），**一个仓库一个明确 Owner**。
- `platform/` 是体系自身的"宪法"：CI 模板、规范文档版本化，规则变更走 MR 评审。

### 4.2 分支模型

- 全项目统一 **trunk-based 简化版**：`main` 常绿 + 短生命周期特性分支 + MR 合入。
- 固件等长发布周期仓库允许 `release/x.y` 维护分支。
- 禁止直接 push `main`（系统强制）。

### 4.3 权限模型

GitLab 五级权限只使用三级：

| 角色 | 权限 | 授予对象 |
|---|---|---|
| Guest/Reporter | 只读 | 跨组查阅人员、外部协作者 |
| Developer | push 分支、建 MR | 本组开发成员 |
| Maintainer | 合 MR、管保护分支 | 每仓库 1–2 名 Owner |

- **禁止任何个人拥有顶层 group 的 Owner 角色**——Owner 只属于平台维护账号，避免出现"新的代码诸侯"。
- LDAP 对接集团域账号（CE 即支持），禁止本地建账号，入离职随域账号自动生效。
  - 边界注（CE 开箱能力）：自动生效的是"登录"——域账号首次登录自动建号、域账号禁用后登录立即失效；分组授权需手动维护（§3.2）。**已绑定的 SSH key 与访问令牌不随域账号禁用自动失效**，需定时脚本比对 AD 禁用名单并调 API 封禁账号（列入阶段 1 实施项）；root 本地账号保留为 break-glass 应急通道，是"禁止本地建账号"的唯一例外。

### 4.4 存量代码收编规则

入仓库门槛：能编译、有 README（用途/Owner/依赖）。**说不清用途的代码不入库**——宁可在迁移中淘汰，不把个人电脑里的混沌原样搬进新体系。

## 5. DLP 共存设计与构建区豁免

设计目标：把与安全部门的谈判变成**交换**而非对抗。

### 5.1 两区模型

| 区域 | DLP Agent | 网络位置 | 放什么 |
|---|---|---|---|
| 办公研发区 | 安装（透明加解密） | 公司办公网 | 工程师笔记本/工作站 |
| 机房构建区 | **豁免** | 隔离网段，仅通内网 | GitLab、Runner、GPU 服务器、镜像/制品库 |

**机制基础**：透明加解密只作用于终端磁盘上的文件，授信进程（git）读出的是明文，push 走 HTTPS/SSH 传输的是明文——GitLab 服务器上落盘的是明文仓库，不带 agent 的 Runner 检出、构建完全正常。**代码的加密边界始终在终端**，这是两区模型成立的机制保证，也是向安全部门解释方案的核心论据。

### 5.2 谈判清单（向 IT/安全申请三件事）

1. **构建区豁免**：GitLab/Runner/制品库服务器不装或仅审计模式装 DLP agent。否则构建产物被加密、Docker 分层缓存全部失效、CI 缓存损坏——流水线根本跑不起来。
2. **终端进程授信**：开发机上 git、ssh、IDE 进入授信进程列表。git 未授信是此类 DLP 最经典的故障：仓库文件被二次加密，push 上去的是密文垃圾，整个仓库污染。
3. **文件类型策略**：源码类扩展名加密；构建产物（.bin/.o/.img 等）不加密——产物要在无数无 agent 的设备（挖机 ECU、现场控制器）上运行，加密产物等于产物不可用。

注：具体授信机制配置（进程白名单粒度、策略格式）需在拿到集团 DLP 产品名后核对其官方文档确认，列入阶段 0 行动项。

### 5.3 交换条件

- 构建区**无外网直连**，pip/npm/docker 拉包一律走内网 Nexus/Harbor 代理镜像，出口收敛、日志可查；
- 机房门禁 + 运维操作审计；
- GitLab 审计日志定期归档，供安全部门随时调阅；
- 驻场终端照常全量装 DLP——**现场笔记本丢在工地上，硬盘上的代码是密文**。

### 5.4 衍生铁律

所有对外交付制品（烧录固件、现场部署包）**必须在构建区构建**，禁止"在我电脑上编译一个先凑合"。同时解决 DLP 加密产物不可用、以及现场版本不可追溯两个问题。

## 6. CI/CD 与制品管理

### 6.1 Runner 池（标签化）

| Runner 池 | 标签 | 硬件形态 | 跑什么 |
|---|---|---|---|
| `fw-build` | docker, cross-* | 机房虚机 ×2 | 固件交叉编译、静态检查 |
| `algo-gpu` | gpu | GPU 服务器注册 | 模型训练、仿真回放测试 |
| `veh-build` | docker | 机房虚机 ×1 | 车载 C++/Qt 构建打包 |
| `cloud-deploy` | docker, deploy | 机房虚机 ×1 | 云端构建部署 |
| `hil-rig` | rig | 接硬件在环台架的实体机 | 手动触发的 HIL 测试 |

GitLab 主机只做调度，不做重活。

### 6.2 流水线三层模型

- **通用层**（`platform/ci-templates`）：以 include 机制提供固件/算法/车载/云端四套模板，新仓库复制即用；规则集中管理。
- **仓库层**：每仓库 override 细节，但必须 include 通用层——不 include 的流水线 MR 不予合入（制度 + 流水线自检双保险）。
- **下游层**（仅固件/算法）：MCU 产物 → 固件签名；模型产物 → 模型评测；通过后才可进入发布流程。

### 6.3 制品晋升与可追溯

- 流水：CI 构建 → 测试环境验证 → 手动批准晋升 → 生产发布。
- **同一 commit hash 的制品从构建到烧进挖机全程可追溯**。
- 发布用 GitLab tag + release 机制。每个发布固件能回答：源码 commit、构建环境（镜像 digest）、签名者、时间。
- 发布物内嵌 `manifest.json`（版本号、commit、构建时间、依赖清单）——现场维护人员一查即知机器上跑的是什么，直接服务驻场场景。

### 6.4 制品与镜像存储分工

| 内容 | 存储 |
|---|---|
| 容器镜像（含 CI 基础镜像、CUDA 训练环境） | Harbor（开源） |
| 二进制制品（Conan/npm/Maven 通用包） | GitLab 内置 package registry |
| 固件 .bin、部署包 | GitLab Release 附件 |
| 大文件（数据集、模型权重） | **不进 git**，放 MinIO 对象存储，git 里只存清单与指针 |

### 6.5 密钥管理

- CI 变量走 GitLab 受保护变量；部署私钥、固件签名密钥放受控主机（CE 无签名集成，用独立小脚本 + 受控主机或 HSM，成本可控），流水线不接触明文密钥。
- 禁止仓库出现任何明文密钥——CE 无 push rules，CI 首条任务跑 gitleaks 补上该缺口。

## 7. 驻场离线工作流

设计原则：**离线为基线、有网为加速**——流程不赌现场有网。

### 7.1 出场前（公司内）

- `git pull` 同步代码 + 从 GitLab Release 下载本次任务相关的**已签名制品**，按目标机器版本打包；
- 按 `platform/` 仓库中的出场 checklist 核对：代码、制品、工具链版本、联系人。

### 7.2 现场三类工作三条通道

| 工作内容 | 通道 | 关键规则 |
|---|---|---|
| 调试、刷固件 | 预构建签名制品 + `manifest.json` 核对 | **现场永远不编译**；要新版本走通道 2 |
| 改代码（bug 修复、参数调整） | DLP 笔记本本地 commit → 有网即 push → MR → CI 构建 → 下载刷入 | 改动**必须**以 commit 形式回中心仓库——防止代码重新散落回个人电脑的硬规则 |
| 取数（日志、传感器数据） | 数据进 MinIO 投放区（现场能连则直传，否则回公司上传） | 数据向内流、代码向外只走 git——方向单一，审计简单 |

### 7.3 现场改码的现实困境与解法

场景：改了一行代码，现场没网，机器等着验证。解法是**本地验证与正式构建分离**：

1. 允许在笔记本上本地编译做**临时验证**；
2. **刷上机器的正式版本必须来自 CI 签名制品**——网络恢复后 push 由 CI 出包，远程指导刷入；
3. 极端情况（断网 + 机器急等）允许刷本地临时包，但**回公司 24 小时内补齐 MR 和正式构建**，否则按违规处理——留应急缝，但缝有账可查。

向团队明确：临时包是救火用的，不是工作方式。

### 7.4 VPN 场景与硬件约束

- 条件好的现场 VPN 回内网直接用 GitLab，体验与公司内一致；**VPN 终端上的 DLP 不因 VPN 而放松**。
- 驻场笔记本全量装 DLP（工地丢失硬盘为密文）；
- 现场 U 盘/移动硬盘按集团外发策略走审批加密盘；
- 现场与挖机 ECU 的物理连接（CAN/以太网调试）纯本地，与 DLP 无冲突。

## 8. 落地路径

| 阶段 | 内容 | 完成标准 | 周期 |
|---|---|---|---|
| 0 盘点与共识 | 全员存量代码盘点（谁有什么、依赖什么、是否在用），产出《存量代码台账》；设计文档送各团队负责人评审——**评审过程即干系人识别过程** | 台账成稿，反对意见逐条归档 | 2–4 周 |
| 0.5 干系人谈判 | 见第 9 节清单，与阶段 0 并行 | 构建区豁免、服务器资源、LDAP 对接有书面结论 | 并行 |
| 1 基础设施 | 机房部署 GitLab（`gitlab-ee` 免费运行）+ runner 虚机 ×2 + Nexus/Harbor 代理 + MinIO | LDAP 域账号可登录、可建 MR、示例流水线全绿 | 2–3 周 |
| 2 收编存量代码 | 按"说得清用途才入库"分批迁移，指定 Owner、补 README、跑通 CI | **个人电脑不再是代码权威副本所在地**（正式宣布的里程碑） | 4–8 周 |
| 2.5 DLP 适配窗口 | 开发机 DLP 铺开时跑授信验证清单（git push/pull、IDE 打开仓库、CI 触发），发现污染立即停、走应急流程 | 验证清单全绿 | 与阶段 2 重叠 |
| 3 CI/CD 深化 | 固件签名、模型评测、HIL 台架接入、OTA manifest 机制 | 近三个月发布的每个固件可回答"源码是什么、谁构建、谁签名" | 持续 |

## 9. 干系人清单

| 找谁 | 谈什么 | 我方给出 | 我方要什么 |
|---|---|---|---|
| 集团信息安全部 | DLP 构建区豁免、授信进程白名单 | 无外网直连的收敛出口、审计日志、驻场终端全量 DLP | 构建区不装 agent、git/IDE 授信 |
| 集团 IT/基础设施 | 服务器资源、LDAP 对接、VPN 策略 | 规范运维承诺（备份、升级窗口） | 机房虚机/物理机、域账号对接 |
| 各团队负责人 | 代码交出来 | 单点丢失风险消除、CI 自动化收益 | 存量代码盘点配合、Owner 认领 |
| 发起人上级 | 立项授权与背书 | 本分阶段可验收计划 | 转发邮件/启动会 |

推进策略落地动作：**阶段 0 主动送出本设计文档评审**，每个反对意见指向一个未覆盖需求或一个待谈判部门，逐条消化。

## 10. 风险与应对

| 风险 | 应对 |
|---|---|
| **人的抵触（最大风险）** | 迁移期间只立规则不追旧账（历史不追究，从今往后按新规则）；强调收益（电脑坏了代码还在、CI 替你跑测试）；Owner 角色给足荣誉感 |
| DLP 谈判破裂（安全部门拒绝构建区豁免） | 降级一：构建区装 agent 但策略降为仅审计；降级二：构建任务回退到装 agent 的虚机跑、接受性能损失。均可接受，不是死局 |
| 平台维护断档 | 指定 1 名兼职平台维护人（发起人起手、规划交接）；无专人照看的单实例 GitLab 两年内必然劣化回混沌 |
| 工程师将代码贴入公有云 AI 工具（DLP 未必覆盖的新泄漏通道） | 制度明确：使用集团批准的 AI 工具或私有化部署，纳入安全培训 |
| 干系人谈判周期不可控（LDAP 对接、服务器资源、DLP 铺开节点均不由本团队掌握） | 阶段 1 / 2.5 的工期从谈判取得书面结论起算，不提前对外承诺日期；谈判期间先做不依赖外方的事：存量盘点、CI 模板编写、Runner 本地验证 |

## 11. 备份容灾

- GitLab 原生全量备份（配置 + 仓库 + 数据库）每日，保留异地/离线副本；
- LDAP、Harbor、MinIO 各自配置快照；
- **MinIO 数据按资产备份**：数据集、模型权重、现场采集数据不是缓存而是资产，其中现场采集数据**不可再生**——按数据分级确定保留与备份策略，纳入与代码同级的容灾要求。数据丢失同样回到"单点丢失"这一本方案要解决的原始问题；
- **恢复演练每半年一次**——未演练过的备份等于没有备份。
