# ADR-0019：原型先行方法论

- 状态：已接受
- 决策日期：2026-08-31 起，经三阶段原型（08-31 / 09-01 / 09-03）确立
- 来源：[原型验证结论](../design/2026-09-07-prototype-verification.md)、[Harbor/MinIO 二阶段设计 §2](../design/2026-09-01-harbor-minio-phase2-design.md)
- 关联：全部 ADR——本 ADR 规定决策如何被验证

## 背景

整套体系在与集团 IT/安全/DLP 谈判之前就要可信；50+ 人推广时不接受"应该可以"。需要一种低成本的验证方式支撑设计文档的每条断言。

## 决策

1. **先原型后正式**：每项机制先在 gitlab-compose-test 本地原型实例上验证（三阶段：平台与权限 → Harbor/MinIO 制品通道 → 需求流），证据（截图、job 日志）编号入档，验证结论页表格化逐项 ✅；
2. **简化项显式列举**：原型用 root 本地账号代替 LDAP、Harbor 用 http + insecure——每项简化都写进"留正式实施"清单，不静默降级；
3. **教程不先于验证**：教程按实际验证路径补写，基于真实实例截图而非手绘理想图；
4. 设计文档逐节与发起人评审确认——评审过程即干系人识别过程。

## 考量

- 设计里的关键断言都有实测编号可引（如：Guest 无 label 权限 → 需求流 §4.1；域 Maintainer 推 platform 被 403 → 权限分离；retry 不重解析模板 → include 机制说明）——"实测"是这套文档的说服力来源；
- 简化项集中列举让"原型 ≠ 正式"的差距可控，正式实施阶段逐项补。

## 否决的备选方案

- 纸面设计直接上正式环境——每条假设都变成生产事故的候选；
- 为原型补齐全部正式细节（真 LDAP、TLS）——被外部依赖（集团 IT）卡死节奏，违反"谈判期间先做不依赖外方的事"。

## 后果

- 正面：设计文档每条断言可追溯到证据；对外沟通（评审、谈判）有演示实例；
- 代价：原型环境本身需维护（compose 栈 ~15 服务），证据链需持续编号归档。

## 重新打开的条件

- 正式实例落地后原型转为演练环境（备份恢复、升级测试），方法论延续。
