# ADR-0015：需求流选型——GitLab 原生轻量

- 状态：已接受
- 决策日期：2026-09-03
- 来源：[产研需求流设计 §2、§3、§11](../superpowers/specs/2026-09-03-requirement-flow-design.md)
- 关联：ADR-0001（同一平台）、ADR-0016/0017/0018（需求流机制）、ADR-0002（CE 能力边界平替）

## 背景

需求与缺陷靠口头与 Excel，来源分散（集团/市场/客户/现场/跨组），交付为版本制节点驱动；团队需求管理经验有限——方案必须实用简洁，流程摩擦足够小，否则口头文化击穿任何规范。

## 决策

用 **GitLab CE 原生能力**搭需求流（Issues + scoped 标签 + 组级里程碑 + 看板）：需求单与代码同库同系统，追溯链由系统自动生成（MR 关单、tag 挂里程碑），零新增运维。

**明确不做**（YAGNI 清单）：固定迭代、工时统计、燃尽图、epics、DORA 度量、外部需求工具对接、发布说明自动生成（先手工复制里程碑清单）。

## 考量

- 根本理由：流程成败不在工具功能多寡，而在**流程摩擦是否足够小**——本方案里"提单→合码→发布→追溯"每一步被系统自动串联，人只需要养成一个新习惯（提单），其余顺路完成；
- CE 无 epic 的平替：任务清单拆子单 + related issues 回链，总单是视图不是工作项；
- 节奏采用版本制、里程碑组织——匹配挖机交付形态，不引入迭代/工时概念。

## 否决的备选方案

- **专业需求工具（禅道/飞书项目）+ GitLab 打通**——需求管理能力强，但双系统双录入、同步需开发维护、审计链跨系统断裂；经验有限的团队先背工具再背流程。保留为集团将来强制统一工具时的对接预留（制度与工具无关，issue 数据可导出迁移）；
- **规范化 Excel + 例会**——不解决追溯与可视化，口头文化击穿任何表格规范。

## 后果

- 正面：需求侧与代码侧同一账号体系、同一权限模型、同一追溯链；教程/权限零新增；
- 代价：需求管理深度受限（无 epic/燃尽/工时）——已在"明确不做"清单里显式接受。

## 重新打开的条件

- CE 能力边界成为真实痛点（跨域需求管理失控、管理层要求工时/燃尽）→ 重议 Premium 或方案 B 对接。
