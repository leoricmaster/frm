# ADR-0013：构建区出口收敛——Harbor/MinIO 通道形态

- 状态：已接受
- 决策日期：2026-08-31（设计 §5.3）；2026-09-01 二阶段原型验证拓扑
- 来源：[统一代码管理体系设计 §5.3](../design/2026-08-31-excavator-code-management-design.md)、[Harbor/MinIO 二阶段验证设计](../design/2026-09-01-harbor-minio-phase2-design.md)
- 关联：ADR-0008（出口收敛是 DLP 豁免的交换条件）、ADR-0011（产物归宿）、ADR-0014（投放区）

## 背景

构建区无外网直连（对安全部门的交换条件），但 CI 必须拉基础镜像、pip/npm 包；大文件与现场数据需要通道。出口必须收敛、可审计。

## 决策

1. **拉包一律走内网代理**：Harbor 代理缓存项目（`docker-hub-proxy`，上游指向可达镜像源）+ Nexus（pip/npm）——哪个 job 拉了什么有迹可循；
2. **Harbor 双项目**：`frm-ci`（业务镜像直推区，build → push → pull 回验）+ `docker-hub-proxy`（代理缓存）——同一系统承担出口仓库与入口口岸两个角色；
3. **MinIO 三桶**：`dataset-model`（数据集/模型权重实体，git 存 sha256 指针清单）、`field-dropzone`（现场数据投放区，**write-only**：只能投、不能删、不能列别人的）、`training-output`（训练产物入库，manifest 记 s3 指针）；
4. 数据流向纪律：**数据向内流、代码向外只走 git**——方向单一，审计简单。

## 考量

- write-only 投放区同时解决"现场能回传"与"现场不能翻别人数据"两个诉求；
- 原型阶段简化项（http + insecure-registries、无 TLS、单节点 MinIO）显式列入"留正式实施"清单，不在原型补。

## 否决的备选方案

- 构建区直连外网拉包——违反交换条件，谈判破裂；
- 每类包一个独立代理系统——运维面扩大，Harbor/Nexus 已覆盖容器与主流包管理器。

## 后果

- 正面：出口单点、日志可查，DLP 谈判的核心筹码落地；
- 代价：代理缓存需运维（上游可达性、缓存清理）；正式实施需补 TLS。

## 重新打开的条件

- 上游镜像源政策变化 / 集团提供统一出口 → 调整代理上游；
- 现场数据量级超出单节点 MinIO → 分布式/纠删码（原型"明确不验证"清单已预留）。
