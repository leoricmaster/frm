# ADR-0006：分支模型——trunk-based 简化版

- 状态：已接受
- 决策日期：2026-08-31
- 来源：[统一代码管理体系设计 §4.2](../design/2026-08-31-excavator-code-management-design.md)
- 关联：ADR-0002（保护分支是系统强制手段）、ADR-0018（无 MR 不合码）

## 背景

分支模型决定日常开发的节奏与摩擦，也决定 MR/CI 评审链是否成立。

## 决策

1. 全项目统一 **trunk-based 简化版**：`main` 常绿 + 短生命周期特性分支（`feat/xxx`、`fix/xxx`）+ MR 合入；
2. **禁止直接 push `main`**——系统强制（保护分支，push/merge 限 Maintainer），不是口头规矩；
3. 固件等长发布周期仓库允许 `release/x.y` 维护分支。

## 考量

- main 常绿是小步快合的前提：分支活得越久，与 main 差异越大，合不回去的代价远大于勤合入；
- "系统强制"优先于"制度约束"：保护分支让越线直接失败，不赌自觉。

## 否决的备选方案

- git-flow（develop/release/hotfix 多长期分支）——流程重，四类代码栈多数用不上，50+ 人里只会被选择性执行；
- 允许长命特性分支——合并成本随时间超线性增长。

## 后果

- 正面：任意时刻 main 可出包；MR 评审链（Closes 关单、CI 门禁）有唯一挂载点；
- 代价：固件发布期需维护 release 分支的 cherry-pick 纪律。

## 重新打开的条件

- 出现 git-flow 才能承载的发布形态（多并行维护版本线）→ 限固件域内重议。
