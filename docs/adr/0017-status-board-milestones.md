# ADR-0017：状态机、看板与里程碑纪律

- 状态：已接受
- 决策日期：2026-09-03
- 来源：[产研需求流设计 §4.3、§4.4、§6、§7.2](../superpowers/specs/2026-09-03-requirement-flow-design.md)
- 关联：ADR-0016（分诊打状态标）、ADR-0018（关单双路径挂在这套状态机上）

## 背景

工作项需要统一状态机供全组看板；进度可视化不引入工时概念；标签若不管控必然蔓延。

## 决策

1. **7 个状态，一个不多一个不少**（全组统一 scoped 标签 `状态::xxx`）：

```
待受理 ─分诊─→ 已排期 ─→ 开发中 ─→ 已关闭        （默认：MR 写 Closes，合入自动关单）
                 │          └─→ 待验证 ─→ 已关闭   （需外部验收：验收人手关）
                 └─→ 暂缓 ─恢复─→ 已排期
分诊打回：待受理 退回提单人补充；已关闭 验收不通过 → 重开回 开发中
受理台终态：已拒绝
```

2. **看板列即状态，状态即例会议程**；周例会只看板、不念稿——"待验证挂了一周的单"自动成为议程；
3. **里程碑 = 版本节点**（命名如 `固件 v2.3·2026Q4批次`），组级跨仓库生效；进度按单数百分比，不做工时与燃尽；
4. **标签字典、看板配置、模板全部在 `platform/` 仓库版本化**——新增一个标签也走 MR，防止标签蔓延失控（平台工程师职责）。

## 考量

- 关单双路径一句话：默认 `Closes #单号` 合入即关（完成定义在 MR 内：CI 绿+自测+评审）；需外部验收（HIL 台架、现场确认、提出方验收）的单只引用不写 Closes，合入后进 `待验证`，验收人手关；
- "7 个一个不多"是防蔓延的硬约束：加状态的理由必须过 ADR/宪法 MR。

## 否决的备选方案

- 自由标签——两周后每人一套词汇，看板作废；
- 工时/燃尽/燃尽图——版本制交付用不上，统计成本先吃掉团队。

## 后果

- 正面：例会零准备成本；状态语义全组一致；管理者视图（组看板 + 里程碑完成度 + 受理台积压）全部 CE 免费；
- 代价：状态机变更需走 platform MR——这是特性（慢即是稳）。

## 重新打开的条件

- 状态不够用成为普遍现象（而非个案）→ 提宪法 MR 加状态，先改本 ADR；
- 升级 Premium/换工具带来新视图能力 → 重议可视化形态。
