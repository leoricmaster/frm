# ADR-0003：仓库结构——单顶层组、按产品域组织

- 状态：已接受
- 决策日期：2026-08-31（intake 归属 2026-09-03 需求流设计补充）
- 来源：[统一代码管理体系设计 §4.1](../design/2026-08-31-excavator-code-management-design.md)、[产研需求流设计 §4.1](../design/2026-09-03-requirement-flow-design.md)
- 关联：ADR-0004（权限沿产品域走）、ADR-0009（platform 宪法仓库）、ADR-0016（intake）

## 背景

50+ 人多团队会重组，代码需要稳定的组织骨架；权限、Owner 责任、看板都沿这个骨架走。

## 决策

1. **唯一顶层组 `excavator`**——正式代码的合法居所只有这一处，个人 namespace 不算数；
2. 第一层子组 = **产品域**：`firmware / autonomy / vehicle / cloud / app / platform`；仓库永远建在第二层（产品域子组内），一仓库一个明确 Owner；
3. 两个例外直挂顶层、不属任何产品域：**`platform/`（宪法：CI 模板、规范、runner 配置，规则变更走 MR）** 与 **`excavator/intake`（受理台，跨域唯一进料口）**。

## 考量

- **团队会重组，产品域相对稳定**——组织维度选变化慢的那个；
- 六个子组名是受控词表：新人从名字推断归属，"我的代码放哪"有唯一答案；
- 跨域的体系设施（宪法、受理台）不属于任何产品，挂顶层避免归属争议。

## 否决的备选方案

- **按团队分子组**——团队一重组，权限/看板/仓库归属全要跟着搬；
- 仓库允许建在顶层根上——破坏"仓库居二层"的唯一性，跨域仓库无处安放的问题已由两个例外显式解决。

## 后果

- 正面：权限沿组继承（本组 Developer / 跨组 Guest-Reporter），里程碑/看板天然按域聚合；
- 代价：跨域新仓库需要先想清楚归哪个域（或立新的例外——那要过评审）。

## 重新打开的条件

- 产品域大调整（新增/合并域）时本 ADR 修订，而非推翻。
