# ADR-0016：受理台与分诊机制

- 状态：已接受
- 决策日期：2026-09-03
- 来源：[产研需求流设计 §4.1、§4.2](../superpowers/specs/2026-09-03-requirement-flow-design.md)
- 关联：ADR-0003（intake 直挂顶层）、ADR-0004（Guest 权限起步）、ADR-0017（状态机）

## 背景

需求来源分散（集团/市场/客户/现场/内部），无统一入口则散落群消息与个人备忘；提单人多数不懂代码住哪。

## 决策

1. **唯一进料口**：顶层 `excavator/intake`（受理台）仓库，所有来源只进这一个口；
2. **谁能提**：全员 Guest 起步（Guest 有建 issue 权限、无代码权限——正好匹配市场/客服）；集团/客户等无账号者由市场或 PM **代提**，单上标注真实来源；
3. **怎么提**：三个 issue 模板三选一——需求（背景/目标/验收标准）、缺陷（现象/复现/影响范围/**manifest 粘贴区**）、任务（技术改进类）；
4. **来源打标**：提单人不打标——**Guest 无 label 权限（三阶段实测）**，`来源::`/`状态::` 标签由分诊人代打；
5. **分诊三动作**：移交（move 到域仓库，评论链接全保留）/ 打回（信息不足退回补充）/ 婉拒（重复或超范围，说明理由关闭）——每产品域 1 名分诊人（Owner 兼任，可周度轮值）；
6. **SLA：3 个工作日内完成分诊**；受理台积压视图公开，积压超一周例会点名。

## 考量

- 独立受理台的代价是多一步移交，换来**提单人不需要知道代码住哪**——多来源场景下的必要隔离；
- 入口响应速度决定大家愿不愿意提单——**3 日 SLA 是口头文化能否被替代的胜负手**；
- 代打标签不是缺陷是分工：Guest 权限门槛足够低（提单零成本），标签质量由分诊人保证。

## 否决的备选方案

- 直接在各域仓库提单——提单人先要弄清"找哪个组哪个仓"，门槛抬高，回到口头；
- 给提单人 label 权限——做不到（Guest 权限所限），且放开后标签质量失控。

## 后果

- 正面：来源统计有数据可依（`来源::` 字典）；分诊瓶颈有视图可问责；
- 代价：分诊是域 Owner 的持续职责，轮值制度需维护。

## 重新打开的条件

- 提单量级大到分诊成为专职工作 → 重议受理台人力配置（机制本身不动）。
