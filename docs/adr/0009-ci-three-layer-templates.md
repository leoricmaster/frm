# ADR-0009：CI 三层模板模型与配置分工

- 状态：已接受
- 决策日期：2026-08-31；配置分工表述 2026-09-07 确认
- 来源：[统一代码管理体系设计 §6.2](../superpowers/specs/2026-08-31-excavator-code-management-design.md)
- 关联：ADR-0003（platform 宪法仓库）、ADR-0004（变更权只归平台组）、ADR-0002（CE include 即支持）

## 背景

CI 配置若每仓库各写各的：重复劳动、规则漂移、"谁配置"无答案；若全部集中：平台组成为所有仓库的瓶颈。需要一个既集中规则又下放细节的结构。

## 决策

**流水线三层模型**：

1. **通用层**（`platform/ci-templates`）：以 include 机制提供固件/算法/车载/云端四套模板，新仓库复制即用；规则集中管理；
2. **仓库层**：每仓库 `.gitlab-ci.yml` include 通用层 + override 本仓库细节；**不 include 通用层的流水线 MR 不予合入**（制度 + 流水线自检双保险）；
3. **下游层**（仅固件/算法）：MCU 产物 → 固件签名；模型产物 → 模型评测；通过后才可进发布流程。

**配置分工**（"怎么跑"集中，"跑什么才算对"下沉）：

| 层 | 谁来配 | 怎么变 |
|---|---|---|
| 通用层模板 | 平台组——变更权只在本组（实测：域 Maintainer 推 platform 被 403） | MR + 评审，合入即全下游生效 |
| 仓库层 override | 业务仓库 Developer 写、Owner 合 | 随代码 MR |
| 基础设施（runner/凭据/制品库） | 平台组 | 配置快照归档 |
| 下游评测标准 | 域定（什么指标算过 autonomy 说了算），机制平台管 | 准入规则进 ci-templates |

## 考量

- include 在流水线创建时解析并快照：模板合入那一刻新规则即挂在所有下游流水线定义上，无需下游配合（注意：retry 不重新解析模板，验证必须触发新流水线——原型实测）；
- 规则版本化、变更走 MR 评审，避免"群里说一声大家改一下"；
- 该模式与开源机器人圈成熟实践同构（industrial_ci 共享模板、ros_buildfarm 集中构建）。

## 否决的备选方案

- 每仓库自治写 CI——规则漂移 + 演化出新的个人黑盒（同方案 B 否决理由）；
- 全集中（平台组替每仓库写流水线）——平台组成为瓶颈，域知识反而在外围。

## 后果

- 正面：规则改一处全项目生效；新人建仓复制模板即得完整流水线；
- 代价：模板变更影响全下游，平台组合入前需自行验证传播（挑下游仓库触发新流水线看 Trace）。

## 重新打开的条件

- 平台组模式被证明无法响应业务节奏（模板变更排队过长）→ 重议分层粒度。
