# ADR-0012：密钥管理

- 状态：已接受
- 决策日期：2026-08-31；凭据打码细节经 2026-09-01 二阶段原型实测
- 来源：[统一代码管理体系设计 §6.5](../superpowers/specs/2026-08-31-excavator-code-management-design.md)
- 关联：ADR-0002（CE 无 push rules）、ADR-0013（Harbor/MinIO 凭据）、ADR-0008（受控主机在构建区）

## 背景

CI 需要各类凭据（Harbor robot account、MinIO access key、部署私钥、签名密钥）；CE 没有 push rules，仓库出现明文密钥时无法在推送时拦截。

## 决策

1. CI 变量走 GitLab **受保护变量**（protected + masked）：只在受保护分支/标签的流水线可见，job 日志一律 `[MASKED]` 打码；
2. 部署私钥、固件签名密钥放**受控主机**（或 HSM），用独立小脚本管理——流水线不接触明文密钥（CE 无签名集成）；
3. 禁止仓库出现任何明文密钥——**CI 首条任务跑 gitleaks** 补 push rules 缺口。

## 考量

- CI 日志谁都能翻：打码让日志可共享排查（红了一起看）而不泄密；
- "流水线不接触明文密钥"把最高危凭据的暴露面限制在受控主机一处。

## 否决的备选方案

- 凭据写进仓库/教程/变量明文——日志与代码双双泄漏面；
- 全面上 Vault 类密钥管理——当前规模过重，受控主机 + 受保护变量够用。

## 后果

- 正面：凭据有单一受控通道；gitleaks 让密钥入库在 CI 层必然被发现；
- 代价：受控主机成为新的运维对象（在构建区内，随 ADR-0008 一起豁免）。

## 重新打开的条件

- 凭据种类/用量超出受控主机模式承载力（多团队共用、轮换自动化需求）→ 评估 Vault / Premium 集成。
