# ADR-0018：三无制度与双向追溯

- 状态：已接受
- 决策日期：2026-09-03
- 来源：[产研需求流设计 §5、§7.1](../superpowers/specs/2026-09-03-requirement-flow-design.md)、[统一代码管理体系设计 §6.3](../superpowers/specs/2026-08-31-excavator-code-management-design.md)
- 关联：ADR-0006（无 MR 不合码）、ADR-0011（manifest）、ADR-0014（现场改动回中心）、ADR-0017（无里程碑不发布）

## 背景

代码侧与需求侧的链路各自成立后，需要宪法级制度把两段焊死，并保证双向可查：从需求到机器、从机器回需求。

## 决策

1. **三无制度**（宪法级，写入 `platform/`，变更走 MR）：
   - **无单不开发**——任何改动（需求、缺陷、现场修复）先有单，commit 必须能追到一张 issue；
   - **无 MR 不合码**——禁直推 main（既有铁律复述入宪法）；
   - **无里程碑不发布**——tag/Release 必须挂里程碑；
2. **正向追溯链**（系统自动生成，不靠人事后补录）：需求单 → MR（Closes + 里程碑）→ CI 绿 → 合入自动关单 → tag/Release（挂里程碑）→ manifest.json（内嵌 commit）→ 烧进机器；
3. **反向追溯链**：现场机器出问题 → 读 manifest → 粘进缺陷模板 → commit 定位 → 该 commit 经哪次 MR → 关联哪张需求单——"这个行为是哪次需求引入的"一查便知；
4. 制度兜底只需 MR 模板 checklist 四项：☑ 关联单号 ☑ 里程碑 ☑ CI 全绿 ☑ 自测通过，Maintainer 合码照单核对。

## 考量

- 现场铁律自动落进需求体系：现场改动必须回 MR（ADR-0014）→ 必须有单——**现场改动天然有单**；
- 临时包刷入的机器 manifest 链是断的，由 24h 补单机制记账——追溯的例外有账，不是盲区；
- 跨域大需求：总单留牵头域仓库，描述里任务清单逐条转 issue，子单 related 回链——CE 无 epic 的轻量替代。

## 否决的备选方案

- 事后补录追溯（人工填表格）——没有人会填，链必然断；
- 只做正向（需求→代码）不做反向——现场排障才是最急需反向链的场景。

## 后果

- 正面：任何一台挖机上跑的行为都能回答"哪次需求引入、哪段代码、谁合入"；"这个版本收了哪些需求"一键列出；
- 代价：三无是制度约束（除禁直推外非系统强制），依赖 checklist 执行与 Owner 把关。

## 重新打开的条件

- 基本不重开；若某条被系统性绕过，优先修执行机制（模板/自检），不是放松制度。
